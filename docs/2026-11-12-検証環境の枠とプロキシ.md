# 検証環境の枠とプロキシ

作成日: 2026-11-12

MISTEMS の検証環境 (`orb-dev-server` スキルと `variant-prep` スキル) を、要件から組み直す。今のツールを前提にせず要件を並べ直し、方式を比べて決めた内容を残す。

## 要件

### ユーザーが挙げた要件

| ID | 要件 |
| --- | --- |
| R1 | ポートの干渉をなくす。ほかのワークツリーだけでなく、ほかのプロジェクトが起動する Web サーバーとも干渉しないようにする |
| R2 | 複数のブランチを一括で検証する。対象は次の 2 つである。(A) 統合待ちのブランチを 1 本ずつ別の環境で動かして並べて確かめる。(C) 並行して作業している複数のワークツリーを、同時に開発モード (HMR あり) で動かす |

### 前のセッションまでに分かっている課題

| ID | 課題 |
| --- | --- |
| R3 | 内蔵ブラウザで開くと、ワークツリーごとにホスト名 (`web.<project>.orb.local`) が違うので、サイトの許可の確認が環境の数だけ出る |
| R4 | 開発モードは `*.orb.local` なので、Claude の規則上テスト用の認証情報 (`admin` / `admin1234`) を入力できず、Claude が自力でログインして検証できない。入力できるのは `localhost`・`*.localhost`・`*.test` などに限られる |
| R5 | 開発モードで vite の HMR の WebSocket (5173 番) に接続できず、画面が「読み込みに失敗しました」になる (2026-11-12、`fix/rss-fetch-safety` と `feat/hashtag-mute-menu` のワークツリー) |

### 今のツールにあり、残す機能

| ID | 機能 |
| --- | --- |
| R6 | LAN 内の実機 (スマホ) から開ける (`--lan`) |
| R7 | seed・スナップショット・restore |
| R8 | 本番ビルドで確かめる (`--prod`、variant) |
| R10 | frontend だけのブランチは、`frontend-variants.yml` を通して本番で切り替えて確かめる (このツールの範囲外。variant-prep が振り分ける) |

R9 (空きメモリが 4GB 未満なら起動しない) は、なくてもよい。今の実装は残すが、要件としては扱わない。

## 制約

- OrbStack の独自ドメイン (`dev.orbstack.domains` ラベル) は `.local` しか使えない ([OrbStack docs: Domains](https://docs.orbstack.dev/docker/domains))。`*.localhost` を使うには、ホストに逆プロキシを置き、ポートを 1 つ公開する必要がある
- Misskey は設定の `url` を 1 つしか持たない。添付・アバター・絵文字などの URL は絶対 URL として DB に残り、seed のスナップショットにも入る。vite の HMR の接続先と `allowedHosts` も `url` から作られる。同じ環境を `url` と違うホスト名で開くと、画像や HMR が壊れる
- Redis のキーの接頭辞は `url` のホスト名から決まる (`packages/backend/src/config.ts` の `redis.prefix` の既定値)
- vite の HMR は `packages/frontend/vite.config.ts` で `hmr.clientPort: 5173` に決め打ちされている。ブラウザは「ページのホスト名の 5173 番」へ直接つなぐ
- 機能ブランチは origin/develop から切るので、`vite.config.ts` を変えるコミットを置く場所がない (claudeImplement に置いても統合した mistems-main にしか入らない)。vite の設定はリポジトリを変えずに差し替える必要がある
- Claude の検証は Playwright MCP (isolated) で行う。ログイン状態はセッションをまたいで残らない。ユーザーに見せるときは内蔵ブラウザを使い、こちらはホスト名ごとに許可の確認が出る

## 方式の比較と決定

### ホスト名の付け方

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A | ワークツリーの名前 (`<project>.localhost`) | `url` が変わらず、seed とログインがそのまま残る | 内蔵ブラウザの許可の確認が環境ごとに出る |
| **B (採用)** | 固定の枠 (`dev1`〜`dev10.localhost`) | 許可の確認が枠の数で終わる | 枠を替えると `url` が変わるので、DB の URL の書き換えが要る |
| C | A を基本にし、見せるときだけ枠を使う | 両方の利点 | B の書き換えの問題が残り、作る量がいちばん多い |

B を採用し、枠を替えたときは DB の URL を書き換えるスクリプトを seed 側に付ける。

### 枠の数と割り当て方

| 案 | 内容 |
| --- | --- |
| **A (採用)** | `up` のときに空いている枠を自動で取り、`down` で返す。`--slot=devN` で指定もできる。埋まっていたら起動しない |
| B | 割り当てを手で行う。枠なしの環境は `*.orb.local` のまま動くので、R4・R5 が残る |
| C | A と同じだが、埋まっていたら最も長く使っていない環境を外す。並行セッションの検証を途中で壊すおそれがある |

枠の数は既定で 10 にし、環境変数 `ORB_DEV_SLOT_COUNT` で変えられるようにする。当初は 1 環境 2〜3GB と見積もって 4 にしたが、2026-11-12 に測ると、OrbStack の VM (12GB) の中で 10 環境が同時に動いており、起動後の web は 1 つ 150MB〜1.7GB だった。重いのは `pnpm install` とビルドの最中だけである

### 開発モードの HMR の通し方

| 案 | 内容 |
| --- | --- |
| **A (採用)** | HMR も枠のプロキシを通す。コンテナの中だけ `clientPort` をプロキシのポートに差し替える |
| B | Caddy をホストの 5173 番にも置く。vite の既定のポートなので、ほかのプロジェクトの vite と必ずぶつかる (R1 に反する) |
| C | 開発モードで HMR を切る。保存のたびに手で再読み込みすることになる |

vite の proxy で HMR を回す案も考えたが、`vite.config.ts` を変えるコミットが要るので採らない。

プロキシのポートは今の 3080 のままにする。80 番はほかのプロジェクトとぶつかりやすいので避ける。

## 設計

### 全体の構成

```
ブラウザ (Playwright・内蔵ブラウザ)
  │  http://dev1.localhost:3080/ … http://dev10.localhost:3080/
  ▼
ホスト 127.0.0.1:3080  ← ホストに公開するポートはこれだけ
  Caddy (共用プロキシ、compose プロジェクト orb-dev-proxy、設定は固定)
  │  Host の 1 つ目のラベル (devN) で振り分ける
  │   ├ /embed_vite/ の vite-hmr の WebSocket → devN.mistems-slot.local:5174
  │   ├ それ以外の vite-hmr の WebSocket     → devN.mistems-slot.local:5173
  │   └ 通常の HTTP と /streaming            → devN.mistems-slot.local:3080
  ▼
各環境 (OrbStack、ワークツリーごとの compose)
  web (pnpm dev か本番ビルド) + db + redis   … ホストにポートは公開しない
  web には OrbStack のラベル dev.orbstack.domains=devN.mistems-slot.local を付ける
```

- **振り分けの名前**: 枠を取った環境の web コンテナに、OrbStack の独自ドメインのラベル `dev.orbstack.domains=devN.mistems-slot.local` を付ける。Caddy は `{http.request.host.labels.1}.mistems-slot.local` へ送るので、枠と環境の対応が変わっても Caddy の設定は変わらない (2026-11-12 に、独自ドメインがほかのコンテナとホストの両方から引けることを確かめた)
- **Misskey の待ち受け**: 枠を取った環境では、Misskey はコンテナの中で 3080 番 (プロキシと同じ番号) で待ち受ける。web コンテナでは `extra_hosts` で `devN.localhost` を 127.0.0.1 に向ける。Misskey が自分の `url` を取りに行くとき (画像のプロキシなど) も、backend が vite へ中継するとき (`url` のホスト名:5173) も、コンテナの中で自分につながる
- **枠の台帳**: `~/.cache/misskey-orb-dev/slots/devN/` というディレクトリを枠ごとに置き、中の `owner` ファイルに compose のプロジェクト名・ワークツリーのパス・取った時刻を書く。枠を取るのは `mkdir` の成否で決めるので、並行セッションが同時に `up` しても同じ枠を取り合わない
- **`up`**: 空いている枠を取り (`--slot=devN` で指定もできる)、`url` を `http://devN.localhost:3080/` にして起動する。前回と `url` が違えば、起動の前に DB の URL を書き換える。開発モードと本番モード (`--prod`) のどちらも枠を使う
- **`up` で枠が埋まっているとき**: 起動せず、台帳 (枠・環境・ワークツリー・取った時刻・コンテナの状態) を表示して止まる
- **既に枠を持つ環境の `up`**: 同じ枠を使い続ける
- **`down`**: 枠を返す。DB と volume は残す。次の `up` で別の枠に入っても、書き換えて使い続けられる
- **台帳の掃除**: 台帳にあっても web コンテナが存在しない環境の枠は、`up` が空きとして扱う (`down` を通らずに環境を消した場合)。コンテナが止まっているだけ (Mac の再起動など) の枠は空きにしない
- **variant**: variant も枠を 1 つ取る。variant が共有するベース環境 (mistems-main) は `--no-slot` で枠を取らずに起動できる。ベースは画面を開かないので、`url` は `http://web.mistems-main.orb.local:3000/` のままで足りる
- **`--lan`**: 今の方式を別のモードとして残す。枠は取らない
- **`slots`**: 新しいサブコマンド。枠・環境・ワークツリー・状態・URL を一覧にする

### HMR の差し替え

- `up` のたびに、ワークツリーの `packages/frontend/vite.config.ts` を読み、`clientPort: 5173` をプロキシのポート (3080) に置き換えたコピーを `~/.cache/misskey-orb-dev/<project>/` に作り、コンテナの中の同じパスに重ねてマウントする。`.config/default.yml` と同じ仕組みである
- 埋め込み (`packages/frontend-embed/vite.config.ts`) も同様に扱う
- 置き換え元の文字列が見つからない (上流で `vite.config.ts` が変わった) ときは、`up` を止めて知らせる。HMR なしで黙って起動しない
- Caddy は、`Sec-WebSocket-Protocol: vite-hmr` のリクエストを、その枠の環境の 5173 番へ回す。パスが `/embed_vite/` で始まるものは 5174 番へ回す (埋め込みの vite の `base` が `/embed_vite/` のため)
- `allowedHosts` は `url` のホスト名 (`devN.localhost`) から作られるので、追加の設定は要らない見込みである

### URL の書き換え (`seed/rewrite-url.mjs`)

- 前回と今回の `url` が違うときに実行する。対象は、`up` で枠が替わったとき、`restore` のあと (スナップショットは保存したときの URL を持つ)、`--lan` との行き来である
- 書き換える列は決め打ちにしない。`public` スキーマの文字列型と jsonb 型の列をすべて走査し、古いオリジンを新しいオリジンに置き換える。上流で URL を持つ列が増えても追いかけ直さずに済む
- 書き換えは 1 つのトランザクションで行う
- 最後に使った `url` は `~/.cache/misskey-orb-dev/<project>/url` に残し、次回の比較に使う。ファイルが無い既存の環境は、`.config/default.yml` の生成物から前回の `url` を読む
- 書き換えたあと、その環境の Redis を空にする (キャッシュが古い URL を持つため)
- variant では書き換えない。種類 2 はベースの DB を共有し、種類 3 の `vdb` はベースの seed から作るので、どちらも DB にはベースの URL (`web.mistems-main.orb.local`) が入っている。ベースが動いていれば画像はそのまま表示される (今の variant と同じ)
- 今の `--lan` の「url を変えたらデータを入れ直す」という制約もなくなる

### ログインの維持

- seed と初回の管理者作成で、`admin` のトークン (`user.token`) を全環境で同じ固定値にする。開発用の値なので、スクリプトの中に書いてコミットしてよい
- ブラウザは枠のホスト名ごとにトークンを覚えているので、枠につなぐ環境を替えても、同じトークンでそのまま入れる見込みである
- 環境ごとに `admin` の ID が違うので、ブラウザに残ったアカウントの一覧と食い違うかもしれない。実装のときに確かめ、食い違うなら seed で `admin` の ID もそろえる。それが難しければログインし直す運用にする (`*.localhost` なので Claude が自分で入力できる)

### スキルの組み直し

- `orb-dev-server` は名前を変えずに作り直す。開発モードの `*.orb.local` と、本番モードの `<project>.localhost` をやめ、どちらも枠にそろえる
- `variant-prep` は手順を変えず、報告する URL を枠のものに替える。統合待ちが空いている枠の数を超えたら、空いている枠の数だけ起動し、残りは報告に「枠待ち」と書く
- 本籍は claudeImplement である

### 検証の流れ

- Claude が自分で確かめるときは、Playwright (isolated) で `http://devN.localhost:3080/` を開き、`admin` / `admin1234` でログインする
- ユーザーに見せるときは、内蔵ブラウザで同じ URL を開く。許可の確認は枠の数 (既定 10 回、1 枠につき最初の 1 回) で終わる
- 並行セッションは、それぞれが `up` して枠を 1 つずつ取る。どのセッションがどの枠かは `slots` で分かる

### 今の環境からの移行

- 共用プロキシの Caddy の設定を、枠の台帳から作る形に置き換える
- 既存の環境は、次の `up` で枠を取り、URL を書き換えて使い続ける。`down -v` は要らない

## 実装したあとに確かめること

1. 2 つのワークツリーを開発モードで同時に起動し、どちらも HMR が効く (ファイルの保存が画面に反映される)
2. 環境を別の枠に入れ直しても、画像が表示され、ログインが続く
3. ほかのプロセスが 5173 番を使っていても、開発モードで起動できる
4. variant を枠で起動できる
5. 枠が埋まっているときに `up` が台帳を表示して止まる
6. Playwright で `devN.localhost:3080` を開き、Claude が `admin` でログインできる
