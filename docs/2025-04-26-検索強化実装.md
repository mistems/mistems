# 検索強化 — フェーズ別実装計画

`検索Index最適化計画.md` の方針をフェーズに分解して実装順を確定するためのワーキングドキュメント。各 Phase は **独立して PR / リリース可能** な粒度で切る。

## 0. 全体像

| Phase | テーマ | 検索停止要否 | REINDEX 要否 | AI 実装目安 |
| --- | --- | --- | --- | --- |
| 1 | 検索 UI: チャンネル指定を並列オプション化 | 不要 | 不要 | 1〜2 時間 |
| 2 | pgroonga 索引にノーマライザ指定を追加 | 不要 (CONCURRENTLY) | **必要** | 1 時間 (人手は数時間〜十数時間の REINDEX 待ち) |
| 3 | MeCab 辞書を NEologd に切替 | 不要 (CONCURRENTLY) | **必要** | 環境構築 + REINDEX で半日〜1日 |
| 4 | MISTEMS 独自の新語辞書 (Wikipedia + 自ログ) を継続運用 | 不要 (CONCURRENTLY) | **継続的に必要** | リポジトリ整備 半日〜1日、運用は継続 |

### 「辞書更新 → REINDEX 必須」の確認

> 質問: 辞書更新したら Index の再作成が必要？

**必須**。pgroonga 索引は内部で「分かち書き後のトークン → 文書 ID」の posting list を持つ。辞書を変えても既存索引内の posting list は古い分かち書きで作られたまま動かない → 新辞書を反映するには `REINDEX` で索引そのものを作り直す必要がある。

- 個別の語を追加・修正するたびに REINDEX するのは現実的ではない (4500 万件で 5〜10 時間 / 本)。
- 運用として **「辞書更新は月次/四半期にまとめる」「REINDEX はメンテウィンドウに集約」** を前提に Phase 4 を設計する。
- REINDEX は `REINDEX INDEX CONCURRENTLY pgroonga_note_text_idx;` で検索を止めずに実行可 (PostgreSQL 12+)。

### Phase 2 と Phase 3 の REINDEX を 1 回にまとめる戦略 (推奨)

Phase 2 (ノーマライザ追加) と Phase 3 (NEologd 切替) はどちらも索引再作成が必要 → **同じメンテウィンドウで両方の SQL を当てて REINDEX 1 回で済ませる** のが運用負荷的に正解。

実装スケジュール案:
1. Phase 1 を先行リリース (UI のみ、REINDEX なし)
2. Phase 2 の SQL 例と Phase 3 の mecabrc 設定を準備
3. メンテウィンドウで `DROP INDEX → CREATE INDEX CONCURRENTLY (新ノーマライザ + NEologd 辞書)` をまとめて実行 → 実質 Phase 2 + Phase 3 同時投入
4. Phase 4 を継続運用フェーズとして開始

## Phase 1: 検索 UI 変更 (チャンネル指定の並列化)

### 背景

現状の `search.note.vue` の検索スコープ MkRadios は **「全て / ローカル / サーバー指定 / ユーザー指定」** の 4 択 (フェデレーション設定により表示は変動)。チャンネル指定は API ではサポート済み (`channelId`) だが UI に出ていない。これを **同じ MkRadios に「チャンネル指定」を 5 つめのオプションとして追加** する。

### 変更箇所

- `packages/frontend/src/pages/search.note.vue`
  - `searchScope` の型に `'channel'` を追加
  - `searchScopeDef` (computed) に `{ value: 'channel', label: i18n... }` を追加 (フェデレーション設定に依存しない並びの末尾)
  - `searchScope === 'channel'` のとき表示するサブオプション UI (MkChannelSelect 的なコンポーネント or 既存パターン流用) を追加
  - `searchParams` (computed) の分岐に「チャンネル指定時は `channelId` を渡す」ロジックを追加
  - `selectChannel()` / `removeChannel()` 関数を追加 (user パターンに合わせる)
- `locales/ja-JP.yml`
  - `_search.searchScopeChannel` 等の新キー追加 (`ja-JP.yml` のみ — 他は Crowdin 自動同期)

### 受け入れ条件

- 検索画面の検索スコープ MkRadios に **「チャンネル指定」** が並ぶ
- 選択時にチャンネル選択 UI が出る (まず 1 つ選んだら他は選べない)
- 検索実行で API に `channelId` が渡る
- channelId 指定検索は host / userId 指定とは排他 (既存仕様)
- 既存の「全て / ローカル / サーバー指定 / ユーザー指定」を選んだときの挙動が壊れていない
- フェデレーション無効インスタンスでもチャンネル指定オプションは表示される (チャンネルは federation 関係ない)

### リスク・注意

- チャンネル選択コンポーネントが既存にあるか要確認 (`MkChannelSelect` 等)。無ければユーザー選択 (`os.selectUser()`) 同等のチャンネル選択 UI 関数を作る必要がある。
- `paramsDef` 側の `channelId` バリデーションは既存。

### AI 実装目安

1〜2 時間。チャンネル選択コンポーネントが既存にあれば短い、無ければ +1 時間。

### 次フェーズへの引き継ぎ

なし。完全独立。

## Phase 2: pgroonga 索引にノーマライザ指定を追加

### 背景

`検索Index最適化計画.md` 4.1 節の方針を実装に落とし込む。現状の example.yml では `WITH (tokenizer='TokenMecab')` のみで、**全角/半角/英数 CI などのゆれを吸収していない**。日本語主体の MISTEMS では体感ヒット率に直接効くため早期に入れたい。

採用するノーマライザ (4.1 節):

```
NormalizerNFKC130("unify_kana", false), NormalizerRemoveBlank
```

### 変更箇所

- `.config/example.yml` / `.config/docker_example.yml`
  - 既存の CREATE INDEX 例 (A: text 単体、B: cw+text 式) に `normalizers = '...'` を追記
- (PostgreSQL ホスト側) 既存索引 A / B の DROP + CREATE INDEX CONCURRENTLY
  - **ドキュメント上に手順を明記**: `docs/search-index-tuning.md` (新設) または `検索Index最適化計画.md` 9 節を参照

### 実行 SQL (本番投入時)

```sql
-- 古い索引を削除 (Phase 3 と同時にやる場合はここで NEologd 辞書も差し替え済みの想定)
DROP INDEX CONCURRENTLY IF EXISTS pgroonga_note_text_idx;
DROP INDEX CONCURRENTLY IF EXISTS pgroonga_note_text_cw_idx;

-- 新ノーマライザ付き索引を作成
CREATE INDEX CONCURRENTLY pgroonga_note_text_idx
  ON note USING pgroonga (text)
  WITH (
    tokenizer  = 'TokenMecab',
    normalizers = 'NormalizerNFKC130("unify_kana", false), NormalizerRemoveBlank'
  );

CREATE INDEX CONCURRENTLY pgroonga_note_text_cw_idx
  ON note USING pgroonga ((coalesce(cw, '') || coalesce(text, '')))
  WITH (
    tokenizer  = 'TokenMecab',
    normalizers = 'NormalizerNFKC130("unify_kana", false), NormalizerRemoveBlank'
  );
```

### 受け入れ条件

- example.yml / docker_example.yml の SQL 例にノーマライザ指定が入っている
- 本番 PostgreSQL ホストで新索引が作成され、`pg_stat_user_indexes` で `idx_scan` が増えていく (= 実際に使われている) ことを確認
- 代表クエリ (例: 「Ａ ＢＣ」 ↔ 「A BC」、「ｺﾝﾋﾟｭｰﾀ」 ↔ 「コンピュータ」) で同じヒット結果になる
- ひらがな ⇔ カタカナの同一視は **起きない** (= `NormalizerAuto` ではなく `unify_kana=false` を指定している効果の確認)

### REINDEX 戦略

- `CREATE INDEX CONCURRENTLY` は本番投入中に走らせて OK (検索は止まらない)
- 完了まで 5〜10 時間/索引 × 2 本 = 約 10〜20 時間 (SSD・余裕あるメモリ前提)
- **完了するまでは旧索引と新索引が両方存在** → ストレージ消費が一時的に倍増。新索引が valid になってから旧索引を DROP
- INVALID 状態で残った場合は `DROP INDEX CONCURRENTLY` で個別削除

### リスク・注意

- メンテウィンドウ中の note INSERT は 旧索引 + 新索引両方への書き込みコストが乗る → 投稿レイテンシ +20〜50ms 程度を見込む
- 失敗時は `pg_index.indisvalid = false` の INVALID 索引が残るのでクリーンアップ手順を運用書に書く

### AI 実装目安

ドキュメント・SQL 整備で 1 時間以内。実 REINDEX は人手 + DB のみで AI 外。

### 次フェーズへの引き継ぎ

**Phase 3 と同じメンテウィンドウで一緒に投入することを強く推奨** (REINDEX 1 回で済ませるため)。実装上は Phase 2 と Phase 3 を **同じ PR** にまとめて、本番手順書として「Phase 2 + 3 同時投入」を案内する。

## Phase 3: MeCab 辞書を NEologd に切替

### 背景

`検索Index最適化計画.md` 4.5 節の NEologd 採用方針を実装。**ipadic デフォルトでは「進撃の巨人」「ポケモンGO」等が誤分割される** ので、NEologd 最終版 (2020-09) を導入する。

### 変更箇所

- **PostgreSQL ホスト** (アプリケーションコード変更なし)
  - NEologd 辞書のインストール
    - `git clone https://github.com/neologd/mecab-ipadic-neologd.git`
    - `cd mecab-ipadic-neologd && ./bin/install-mecab-ipadic-neologd -n -y -p /usr/lib/mecab/dic/mecab-ipadic-neologd`
  - `/etc/mecabrc` の `dicdir =` を NEologd ディレクトリに変更
  - PostgreSQL サービス再起動 (mecab を fork 起動するプロセスがリロードを必要とする)
- **本リポジトリ側のドキュメント**:
  - `.config/example.yml` / `docker_example.yml` の `sqlPgroonga` セクションに「NEologd を使いたい場合は別途辞書を用意し /etc/mecabrc を差し替えること」とコメント追記
  - `docs/search-index-tuning.md` (新設) に NEologd インストール手順を記載

### 実行手順 (本番投入時)

1. ステージング環境で NEologd を入れた mecab に「進撃の巨人」等を流して、1 トークン化されることを `mecab -d /path/to/neologd` で確認
2. PostgreSQL ホスト本番にも同様に NEologd を配置 + mecabrc 切替 + PostgreSQL 再起動
3. Phase 2 の SQL (ノーマライザ付き CREATE INDEX) を CONCURRENTLY で実行
4. 旧索引を DROP

> Phase 2 を同じウィンドウで実行することで、新索引は **「ノーマライザ + NEologd 辞書」両方適用済み** で構築される → REINDEX 1 回で 2 つの改善が乗る。

### 受け入れ条件

- 本番 PostgreSQL ホストで `mecab` コマンドが NEologd 辞書を読んでいる (`mecab -D` で確認)
- 代表クエリで効果検証:
  - 「進撃の巨人」検索: ipadic では「進撃 AND の AND 巨人」、NEologd では 1 語マッチ → ヒット数 / 精度の差を実データで計測
  - 「ポケモンGO」「ハッピーセット」等の固有名詞も同様
- 索引構築時間が ipadic 比 +10〜30% 程度に収まっている
- 索引サイズが極端に増えていない (posting list は短くなる傾向)

### REINDEX 戦略

Phase 2 と同じ。**Phase 2 + Phase 3 を同一メンテウィンドウで REINDEX 1 回**。

### リスク・注意

- NEologd 辞書サイズ 約 800MB 〜 1GB。PostgreSQL ホストのディスク容量を確認
- mecabrc 切替後の再起動を忘れると pgroonga は古い辞書のままで動く
- 他に mecab を使うサービスが同居している場合は dicdir 競合に注意 (`--dicdir` で明示指定するか、専用 mecabrc を用意して環境変数で指す)
- NEologd 公式更新が止まっているため、これだけでは「2020 以降の新語」は拾えない → Phase 4 へつなぐ

### AI 実装目安

ドキュメント整備 1 時間以内。本番作業は PostgreSQL ホスト側で半日 (辞書ビルド + REINDEX 含めると 1 日コース)。

### 次フェーズへの引き継ぎ

NEologd が動いている前提で Phase 4 のカスタム辞書ビルドフローを設計する。Phase 4 は NEologd を **ベースとして上書き** するので、NEologd 配置パスを Phase 4 のビルドが知っている必要あり。

## Phase 4: MISTEMS 独自の新語辞書整備 (継続運用)

### 背景

`検索Index最適化計画.md` 4.6 節の方針を実装フェーズに分解。NEologd の 2020 以降の空白を埋め、MISTEMS 固有の語彙 (フォーク名・コミュニティ用語・最近のゲーム/アニメ) を継続的に追加していく仕組みを作る。

### 4.1. リポジトリ初期化

private リポジトリ **`mistems-mecab-dic`** を新規作成 (GitHub private / Forgejo private)。

```
mistems-mecab-dic/
├── seed/                          # ipadic + NEologd seed (git submodule)
├── patches/
│   ├── games.csv                  # ゲーム本作タイトル
│   ├── games-abbrev.csv           # ゲームの略称・俗称
│   ├── anime.csv                  # アニメ・漫画
│   ├── vtuber.csv                 # VTuber 名 / グループ
│   ├── meme.csv                   # SNS ミーム
│   ├── mistems-internal.csv       # MISTEMS フォーク固有用語
│   └── community.csv              # コミュニティ提案語の溜まり場
├── scripts/
│   ├── normalize-csv.sh           # nkf で UTF-8 化、改行統一
│   ├── validate.py                # 重複・フォーマット・カタカナ読み検証
│   ├── extract-wikipedia.py       # Wikipedia ダンプ → 候補 CSV
│   ├── extract-unknown-words.py   # 自インスタンスログ → 未知語候補 CSV
│   └── build.sh                   # seed + patches → out.csv → mecab-dict-index → sys.dic
├── .github/workflows/
│   ├── ci.yml                     # PR で validate.py
│   └── nightly-build.yml          # 毎晩 build.sh → アーティファクト
└── README.md
```

### 4.2. 大量取得スクリプト: Wikipedia ダンプ → 候補 CSV

`scripts/extract-wikipedia.py`:

- 入力: jawiki 月次ダンプ (`jawiki-latest-pages-articles.xml.bz2`)
- 抽出対象カテゴリ: `Category:○○年のコンピュータゲーム` `Category:日本のテレビアニメ作品 (2020年代)` `Category:バーチャルYouTuber` 等
- 各記事の冒頭から「読み」を抽出 (`{{読み|}}` テンプレート / 記事冒頭の `'''...'''（よみ）`)
- 出力: `candidates/wikipedia-games-YYYYMM.csv` 等の **候補 CSV** (CC BY-SA 表記付き)
- 候補 CSV は手動レビューで `patches/` に取り込む (= 全自動マージはしない)

### 4.3. 継続更新スクリプト: 自インスタンスログ → 未知語候補

`scripts/extract-unknown-words.py`:

- 入力: 最近 N 日の note テキスト (もしくは検索クエリログ)
- 処理:
  1. テキストを MeCab (NEologd + 現状の patches/) で分かち書き
  2. 未知語 (品詞が `名詞,固有名詞,一般,*,*,*` だが `品詞細分類` が一致しないもの、または品詞不明 `名詞,サ変接続` 等で連続するもの) を集計
  3. 出現頻度 > しきい値 のものを候補 CSV に出力
- 出力: `candidates/unknown-words-YYYYMM.csv`
- 月次レポートとして PR を自動作成、レビュアーが取捨選択

### 4.4. CI/CD パイプライン

- **PR 時** (`ci.yml`):
  - `normalize-csv.sh` で UTF-8 / LF 確認
  - `validate.py` で重複・フォーマット・読みが半角カタカナでないこと等を検証
  - 検証 fail なら PR ブロック
- **マージ時 / nightly** (`nightly-build.yml`):
  - `build.sh` で seed + patches を結合 → `mecab-dict-index` → `sys.dic` を生成
  - 成果物 (sys.dic + ライセンス表記) をアーティファクトとして保管
  - Git 本体には sys.dic を入れない (バイナリ肥大化防止)
- **リリース**:
  - 月次でアーティファクトを取得 → ステージング → 本番 PostgreSQL ホストへ配置
  - mecabrc は変えない (パスは固定)
  - **`REINDEX INDEX CONCURRENTLY` を該当索引すべてに実行**

### 4.5. REINDEX 運用 (回答の核心)

辞書を更新したら、新辞書での分かち書きを反映するために **既存索引すべての REINDEX が必須**。具体的な運用フロー:

```
[辞書更新リリース手順]
1. ステージング DB で新 sys.dic を配置 + REINDEX INDEX CONCURRENTLY → 検索結果が想定通り変わることを確認
2. 本番メンテウィンドウ (例: 月末週末) を確保
3. 本番 PostgreSQL ホストに sys.dic を配置
4. 順番に REINDEX INDEX CONCURRENTLY:
   - pgroonga_note_text_idx
   - pgroonga_note_text_cw_idx
   - (採用していれば) pgroonga_note_local_text_idx, pgroonga_note_local_text_cw_idx
5. 完了後、pg_stat_user_indexes と検索 API レイテンシを監視
```

### 4.6. リリースサイクル設計

- **月次リリース** を基本とする (例: 第 4 土曜のメンテウィンドウ)
- 緊急の語彙追加要望が来ても、**REINDEX のコストが大きいので月次に集約** することを運用書に明記
- 例外: バイラルなミーム / 大ヒットゲーム発売時のホットフィックス枠として年数回まで許容

### 受け入れ条件

- `mistems-mecab-dic` リポジトリが初期化され、最低 1 回 CI が緑になっている
- `extract-wikipedia.py` で 1 カテゴリの候補 CSV が生成できる
- `extract-unknown-words.py` でステージング DB から候補 CSV が生成できる
- nightly-build.yml がアーティファクトとして sys.dic を出している
- ステージング環境で sys.dic 配置 + REINDEX を 1 周回し、検索結果に変化が出ることを確認
- 「月次リリース手順書」が docs にある

### AI 実装目安

- リポジトリ初期化 + 基本ファイル + 初期 patches/ + CI 設定: 半日
- `extract-wikipedia.py` プロトタイプ: 半日 (Wikipedia ダンプの XML パース + テンプレ抽出)
- `extract-unknown-words.py` プロトタイプ: 半日 (MeCab Python バインディング + 集計)
- **合計 1.5〜2 日** のプロトタイプ作成期間。本番運用に乗るまでは初回 REINDEX も含めて 1 週間

### リスク・注意

- 4500 万件 × 索引 4 本の REINDEX を月次で回すと、月の数日が常にメンテ状態 → メンテ枠が逼迫する場合は **「Phase 4 の本番 REINDEX は四半期 1 回」「途中で追加された語彙は次サイクルまで保留」** を採用
- 候補 CSV を全部取り込まない判断が重要 (ノイズ追加で精度が下がるリスク)
- ライセンス管理: Wikipedia 由来は CC BY-SA、出典をパッチ CSV のヘッダコメントに残す

## 横断トピック

### REINDEX 戦略まとめ

| トリガー | 対象 | 実行方法 | 頻度 |
| --- | --- | --- | --- |
| Phase 2 (ノーマライザ追加) | A / B | CREATE 新 → DROP 旧 | 1 回 |
| Phase 3 (NEologd 切替) | A / B | Phase 2 と同時 | 1 回 |
| Phase 4 (新語辞書追加) | A / B / (C / C') | `REINDEX INDEX CONCURRENTLY` | 月次〜四半期 |
| pgroonga バージョン更新 | 全索引 | 同上 | 不定期 |

### メンテナンスウィンドウ

- 月次の固定枠 (例: 第 4 土曜 02:00-06:00 JST) を運用書に明記
- REINDEX 中も検索は止まらないが、書き込みレイテンシが上がるので投稿が多い時間帯は避ける

### ロールバック

- Phase 2 / Phase 3 投入後に問題が出たら、旧索引を残しておけば DROP した新索引を再構築する必要はない
- → **「新索引 CONCURRENTLY 作成 → 動作確認 → 旧索引 DROP」**の順を守る
- Phase 4 の sys.dic はバージョンタグでロールバック可能 (前月版に戻して REINDEX 再実行)
