# 開発用シードデータ（Seeder とスナップショット）Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `orb-dev-server` で立てた Misskey に、動作確認用のデータ（ユーザー約 50 人（うちリモート 10 人）・ノートは 1 人あたり約 700 件で合計約 3 万 5 千件・カスタム絵文字約 100 個・プロフィール画像など）を、いつでも同じ内容で入れられるようにする。2 回目以降はスナップショットから数十秒で戻せるようにする。

**Architecture:** Seeder が正本で、スナップショットはそのキャッシュである。Seeder は 2 段に分ける。API の段では、ユーザー、プロフィール、絵文字、フォロー、チャンネルなどの「骨組み」と、通知やカウンタの整合を本体に任せたい「やりとり」のノート（数百件）を作る。SQL の段では、量の大半を占めるノート（ローカル約 2 万 8 千件、リモート約 7 千件）とそのリアクション、API では作れないリモート（連合）のデータを、過去の日付に散らばらせて DB に直接入れる。API で 3 万件を作ると数十分かかり、時刻もすべて実行時点に固まるためである。どちらも `orb-dev.sh` のサブコマンドから呼ぶ。API の段は web コンテナの中で `http://localhost:3000` に向けて実行する（ホストの Node.js から orb.local の名前を引けないことがあるため）。SQL の段は db コンテナの psql に流し込む。スナップショットは `pg_dump` と、アップロード済みファイルの `files/` の tar を組にして保存し、DB の最新 migration 名をキーにする。

**Tech Stack:** bash（`orb-dev.sh`）、Node.js 26（依存なしの ESM スクリプト。`fetch`、`zlib`、`crypto` だけを使う）、PostgreSQL 18（`pg_dump` / `pg_restore` / `psql`）、Redis 7、OrbStack（docker compose）

**Spec:** 独立した仕様書はない。下の「設計」節が仕様を兼ねる（2026-10-23 のセッションで合意した内容）。

### サブコマンド

| コマンド | 動作 |
|---|---|
| `orb-dev.sh up [worktree] [--prod]` | 既存の起動。`--prod` を付けると `pnpm dev` の代わりに `pnpm build → pnpm migrate → pnpm start` で起動する |
| `orb-dev.sh seed [worktree]` | 起動中の環境に Seeder を流す。終わったら自動でスナップショットを取る |
| `orb-dev.sh snapshot [worktree] [名前]` | 今の DB と `files/` を保存する。名前の既定は `seed` |
| `orb-dev.sh restore [worktree] [名前]` | 保存したものに戻す。キー（最新 migration 名）が合わなければ失敗し、`seed` をやり直すよう案内する |
| `orb-dev.sh up [worktree] --seed` | 起動後、キーの合うスナップショットがあれば `restore`、なければ `seed` を実行する |

スナップショットは `~/.cache/misskey-orb-dev/<project>/snapshots/<最新 migration 名>/<名前>.dump` と `<名前>.files.tar` に保存する。最新 migration 名は `SELECT name FROM migrations ORDER BY id DESC LIMIT 1` で取る。

### データの中身

乱数はシード値（既定 `20261023`、環境変数 `SEED` で変更できる）で固定し、何度流しても同じ内容にする。

**ローカル（API で作る）**

| 種類 | 量・内容 |
|---|---|
| ユーザー | 管理者 `admin` に加えて 39 人（`user01`〜`user39`）。リモートの 10 人と合わせて約 50 人になる。パスワードはすべて `admin1234`。`user38` と `user39` は `isBot`。全員に生成したアバターとバナー、表示名（乱数で作る日本語風の名前）、自己紹介、プロフィールの追加情報（fields）0〜3 件を設定する。アバターやバナーを設定しない人も 1 割混ぜる |

| フォロー | 下の「フォロー関係」のとおり。ローカルどうしは API（`following/create`）で作る |
| カスタム絵文字 | 生成した画像で 100 個。カテゴリ 8 つに分け（カテゴリなしも数個）、エイリアスを付ける。2 個はセンシティブ、2 個はローカルのみ、数個にライセンス表記を付ける |

| アンケート | 10 件（API で作る）。うち 1 件は締め切りが 2 分後、1 件は 1 日後、残りは締め切りなし |
| リアクション（やりとり） | API で作ったノートの 3 割に、Unicode とカスタム絵文字で 1〜6 個 |
| クリップ | `admin` に 15 件（11 件以上ないとページネーションの確認ができないため）。うち 3 件に 5〜10 ノートを入れる。`user01` のクリップ 2 件を `admin` がお気に入りにする |
| チャンネル | 3 つ。それぞれに 20〜40 件の投稿。`admin` が 2 つをフォローし、1 つをお気に入りにする |
| リスト・アンテナ | `admin` にリスト 2 つとアンテナ 1 つ |
| お気に入り | `admin` がノート 10 件をお気に入りにする |
| 通知 | 上のやりとりで自然に発生する（フォロー、リアクション、リプライ、メンション、リノート、アンケートの締め切り） |

API で作るノートの時刻は、すべて実行した時点になる（作成日時を指定する API はない）。過去の日付に散らばったデータは、SQL の段で入れる大量のノートで確かめる。

| 種類 | 量・内容 |
|---|---|
| インスタンス | 2 つ（`remote-a.example`（softwareName `misskey`）と `remote-b.example`（softwareName `mastodon`））。名前、themeColor、iconUrl を設定し、インスタンスティッカーが出るようにする |
| ユーザー | 2 つのインスタンスに 5 人ずつ、計 10 人。`uri`、`inbox`、`sharedInbox`、`followersUri`、`lastFetchedAt` を入れる。アバターとバナーは、ローカルで生成した画像を `isLink` のリモート用 drive_file として登録し、その ID を指す |
| ローカルのノート | ローカル 40 人に 1 人あたり約 700 件（600〜800 件）、計約 2 万 8 千件。時刻は過去 180 日に散らばらせ、人ごとに投稿する時間帯の癖を付ける（ID を過去の時刻で生成する）。本文の種類（普通の文、MFM、ハッシュタグ、CW、ローカルのカスタム絵文字）は API の段と同じ割合にする。添付は、API の段でアップロードした画像のファイル ID を使い回す |

| リアクション（大量分） | 大量のノートの 2 割に、ローカルとリモートのユーザーから 1〜10 個（`note_reaction` を入れ、`note.reactions` の jsonb を合わせる） |
| リモートのカスタム絵文字 | 各インスタンスに 4 個（`host` を設定。画像はローカルで生成したものの URL を使う） |
| フォロー | 下の「フォロー関係」のうち、リモートが関わるものを `following` テーブルに直接入れる。`user.followingCount` / `followersCount` も更新する |

### フォロー関係

ローカル 40 人とリモート 10 人の計 50 人を、次の 4 つの型に分ける。どの型に誰が入るかは乱数で決め（シード値で固定）、ローカルとリモートを混ぜる。`admin` は相互フォローの型に入れる。

| 型 | 人数 | 内容 | 確かめたいこと |
|---|---|---|---|
| 相互フォローの輪 | 約 17 人 | 輪の中で互いにフォローする（全員ではなく、1 人あたり 4〜10 人） | 普通のホームタイムライン、通知、フォロー中のノート |
| フォローしているだけ | 約 8 人 | 輪の人をフォローするが、誰からもフォローされない | フォロワー 0 人の表示、片方向の関係 |
| フォローされているだけ | 約 10 人 | 誰もフォローしないが、輪の人からフォローされる | フォロー 0 人・フォロワーありの表示 |
| 孤立 | 約 15 人 | 誰もフォローせず、誰からもフォローされない | ホームタイムラインが空のときの誘導、フォロー 0 人の表示 |

「誰もフォローしていない人」は、「フォローされているだけ」と「孤立」を合わせて約 25 人（約半分）になる。

直接入れた行は、`user.notesCount`、`instance.notesCount`、`instance.usersCount` などのカウンタも SQL で合わせる。ハッシュタグは `hashtag` テーブルにも反映する（ハッシュタグのページと「みつける」のトレンドが空にならないようにする）。3 万件を超える INSERT は、1 文あたり 1000 行の複数行 INSERT にまとめ、全体を 1 つのトランザクションにする。

### タイムラインの扱い

SQL で入れたリモートのノートは、Redis のタイムラインキャッシュ（FTT）には載らない。そこで Seeder は、最初に `admin/update-meta` で `enableFanoutTimeline: false` にする。こうするとタイムラインが DB から組み立てられるので、リモートのノートも出る。FTT の動作を確かめたいときは、seed の後に管理画面から戻す。`restore` の後は Redis を `FLUSHALL` する。

### 対象外

- 実際の連合（別のサーバーとの ActivityPub のやりとり）は扱わない。リモートのユーザーやノートは表示用のデータで、取得し直そうとすると失敗する
- 本番データの取り込みは扱わない（個人情報を含むため）
- ノート数千件以上の負荷試験用データは扱わない（量は環境変数 `SEED_LOCAL_NOTES` / `SEED_REMOTE_NOTES` で増やせるようにだけしておく）
