# RSS の取得を安全にする（safer-rss の作り直し）

作成: 2026-11-12。ブランチ `fix/rss-fetch-safety`（最新の `origin/develop` から切った）。

## 目的

元のブランチと、mistems/mistems の PR#46「Safer rss」(2025-01、2026-11-11 に閉じた) のコメントから読み取った。PR のコメントには、生のエラーログが大量に流れること、RSS でない URL (`http://feeds.afpbb.com/rss/afpbb/afpbbnew` など) を入れるとずっと読み込み中になること、フロントエンドで間隔の既定値と下限を延ばしたいことが書かれていた。生のエラーログは、本家で失敗を ApiError で返すようになって解決している。

元のブランチ `safe-rss`（2025-01）の目的は 2 つだった。

1. `fetch-rss` が、URL でない入力・RSS でないページ・存在しないドメインで 500 になるのを防ぎ、ウィジェットに分かる形で返す。失敗が続く URL は取りに行かない
2. RSS のウィジェットとステータスバーの取り直しの間隔（既定 60〜120 秒）を延ばし、サーバーと相手のサイトへの負荷を減らす（最小 45 分、既定 180 分）

元のブランチは本家の大きな変更と衝突して統合から外れていた。また、秒とミリ秒の取り違え（`Math.max(60 * 45, 秒 * 1000)`、`分 * 1000` など）や、失敗の回数を数える表がずっと増え続ける問題があった。

## 本家ですでに入っていたこと

本家の develop で、`fetch-rss` の安全化はかなり進んでいた（2026-11 時点）。

- URL の検査（長さ・`http`/`https` だけ・認証情報を含まない）、応答サイズの上限（1 MiB）、同時実行数の上限（32）、同じ URL の同時の取得をまとめる処理
- 失敗は 500 ではなく ApiError（`INVALID_URL` 400、`FETCH_RSS_FAILED` 422、`FETCH_RSS_UNAVAILABLE` 503）で返す
- ウィジェットの項目のリンクの検査（`javascript:` などを除く）

## 残っていた問題と、作り直した形

### サーバー: 失敗した URL を何度も取りに行く

- 成功した応答には `Cache-Control: public, max-age=180` が付くが、失敗した応答には付かない。壊れた URL を置いたウィジェットがあると、置いた人の数だけ、取り直しのたびにサーバーが相手のサイトへ取りに行く
- 取得に失敗した URL（正規化したもの）を 10 分覚え、その間は取りに行かずに `FETCH_RSS_FAILED` を返す。覚えるのは 1,000 件までで、超えたら古いものから捨てる（元のブランチの表は増え続けていた）
- 同時実行の上限で断ったとき（`FETCH_RSS_UNAVAILABLE`）と、URL が正しくないとき（`INVALID_URL`）は覚えない

### 画面: 失敗すると読み込み中のまま止まる

- ウィジェットは応答を確かめずに `res.json()` をフィードとして読んでいたので、エラーの応答で `feed.items` が `undefined` になって例外を投げ、読み込み中の表示が出たままになっていた
- 共通の処理 `utility/fetch-rss.ts` の `fetchRssItems()` にまとめ、エラーの応答・通信の失敗・`items` のない応答では `null` を返すようにした。項目のリンクの検査もここに移した
- 取れなかったときは読み込み中の表示を止める。前に取れた項目があればそれを出したままにし、なければ RSS ウィジェットはエラーの表示、ティッカーは「問題が発生しました」を出す。ステータスバーは何も出さない（これまでと同じ）

### 画面: 取り直しの間隔が短く、秒で入力させていた

- 元のブランチの決め方どおり、下限を 45 分、既定を 180 分にした（`RSS_MIN_REFRESH_INTERVAL_MIN`・`RSS_DEFAULT_REFRESH_INTERVAL_MIN`）。mistems/mistems の Issue#43「やりたいことリスト」の「RSSウィジェットの最小単位を15秒から45分にする」にあたる
- 設定は分で入力する。ウィジェット（RSS・ティッカー）の設定は、秒の数値欄（`refreshIntervalSec`）をやめ、分のスライダー（`refreshIntervalMin`、45〜1,440 分、15 分刻み）にした。ラベルは `_widgetOptions._rss.refreshIntervalMin`（「更新間隔(分)」）を足した
  - 保存済みの秒の設定は読まなくなるので、既定の 180 分になる。これまでの値はほとんどが 45 分未満で、下限に引き上げられるので、影響は 45 分より長く設定していた人に限られる
- ステータスバーの設定は、連合・リストのステータスバーと共通で秒で保存しているので、保存の形は変えない。RSS の設定画面だけ、分のスライダーで入力して秒に直して保存する。種類を RSS に切り替えたときの既定値は 180 分にした

## テスト

- backend unit（`test/unit/server/api/endpoints/fetch-rss.ts`、19 件）: 失敗した URL を 10 分は取りに行かず過ぎたら取りに行くこと、正規化して同じ URL も同じに扱うこと、ほかの URL に影響しないこと、同時実行の上限で断ったものは覚えないこと。既存のテスト 1 件（失敗のあと同じ URL を取り直して枠が空いたことを確かめるもの）は、失敗を覚える挙動に合わせて別の URL で確かめる形にした。修正前のコードでは、10 分の間は取りに行かないことのテストが失敗する
- frontend unit（`test/unit/fetch-rss.test.ts`、8 件）: 間隔を分で受け取ること・下限と既定値・ステータスバーの秒の値の扱い、リンクの検査、エラーの応答・通信の失敗・`items` のない応答で `null` を返すこと
- `vue-tsc` と lint が通る

### レビューで直したこと

`vue-component-reviewer` の指摘を受けて、ウィジェット（RSS・ティッカー）を次のように直した。

- URL を変えたら、前の URL で取れた項目を消し、読み込み中に戻す。「前に取れた項目を出したままにする」のは同じ URL のときだけにする
- 取得中に URL を変えたときは、古い応答を捨てる（取得ごとに世代の番号を付ける）
- 取り直しの間隔を変えると、定期取得が止まっていた（本家からある不具合）。`useInterval()` は `onMounted` で始めるので、マウントのあとに watcher の中で呼び直すと開始されない。`createVisibilityAwareInterval()` を直接使い、アンマウントで止めるようにした。タブが裏にある間は止める挙動はそのまま
- 設定画面から下限が分からない点（ウィジェットの数値の設定には下限を付けられない）は、実行時に下限で抑えるので、そのままにした

### 設定画面を閉じる前に、URL が正しいか分かるようにする（2026-11-12 追加）

ウィジェットの設定画面（`MkWidgetSettingsDialog.vue`）には、入力中の設定で動くプレビューがある。URL の欄で保存すると、プレビューがその URL で取得し直す。取れないときはエラーを出すようになったが、理由が分からなかったので、次のようにした。

- `utility/fetch-rss.ts` の `fetchRss()` は、取れなかった理由（`RssFetchError`）を返す。サーバーのエラーコードから見分ける
  - `INVALID_URL` → 「URL の形式が正しくありません」
  - `FETCH_RSS_FAILED` → 「RSS を取得できませんでした。RSS ではないページか、サイトに接続できない可能性があります」
  - `FETCH_RSS_RECENTLY_FAILED` → 「少し前に取得に失敗した URL です。10 分ほどたってから、もう一度試してください」
  - `FETCH_RSS_UNAVAILABLE` → 「サーバーが混み合っています。しばらくしてから、もう一度試してください」
  - それ以外（通信の失敗など） → 「問題が発生しました」
  - 文は `ja-JP.yml` の `_rssFetchError` に置いた
- サーバーは、覚えた失敗で断るとき、`FETCH_RSS_FAILED` ではなく新しいエラー `FETCH_RSS_RECENTLY_FAILED`（422）を返す。サイトが一時的に落ちていて同じ URL で試し直したとき、取りに行っていないことが分かる。覚えた失敗を設定画面からだけ無視する口は作らない（誰でもその口を使って、失敗を覚える仕組みを素通りできてしまうため）
- RSS ウィジェットはエラーの表示（`MkResult`）に、ティッカーは警告のアイコンの横に、理由の文を出す。ステータスバーは設定画面にプレビューがないので、これまでどおり何も出さない
- misskey-js の自動生成ファイルには API のエラーが含まれないので、`pnpm build-misskey-js-with-types` を実行しても差分はなかった
- テスト: frontend unit は 13 件（エラーコードごとの理由、通信の失敗、`items` のない応答、理由ごとの文）、backend unit は 19 件（覚えた失敗で断ったときのエラーコード）

### 間隔の入力欄、ステータスバーのプレビュー、ステータスバーの URL の反映（2026-11-12 追加）

- **ステータスバーで URL を変えても表示が切り替わらなかった**: `statusbar-rss.vue` は取得のたびに `props.url` を読むだけで、URL の変化を watch していなかった。`statusbars.vue` はステータスバーの `id` を key にしているので、URL を変えても同じコンポーネントが使い続けられ、次の取り直し（45 分以上あと）まで前のフィードを流していた。間隔を変えてもタイマーを作り直していなかった。フィードの取得（URL の変化で取り直す、間隔の変化でタイマーを作り直す、古い応答を捨てる）を `utility/use-rss-feed.ts` の `useRssFeed()` にまとめ、ウィジェット・ティッカー・ステータスバーで使う
- **取り直しの間隔**: スライダーでは今の値が分からないので、単位（分）と範囲（45〜1,440 分）を添えた数値の入力欄にした。範囲の外の値・小数・数でない値は保存しない。ウィジェットの設定では完了ボタンを押せなくし、ステータスバーの設定では保存せずに注意書きを赤くする。`MkForm` の number の項目に `min`・`max`・`suffix` を足した
- **ステータスバーの設定画面のプレビュー**: URL の入力欄の下に `MkRssFeedPreview`（フィードのタイトル・件数・項目、取れなかったときは理由）を出し、確かめてから保存ボタンで保存する。プレビューは入力が 1 秒止まってから取りに行く。明らかに URL でないもの（空欄、http・https 以外）は、`fetchRss()` がサーバーに問い合わせずに `invalidUrl` を返す。項目の一覧（取得中・理由・空・項目）は `MkRssFeedItems` にまとめ、RSS ウィジェットと共通にした
- テスト: frontend unit は 20 件（間隔の入力値の検査、フィードのタイトル、URL でないものを問い合わせないこと）
