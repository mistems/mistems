# /api/stats のリアクション数概算の仕上げ

作成: 2026-11-12。ブランチ `perf/stats-reaction-count-estimate`（既存。riin に push 済み）。

元の計画書はブランチの `docs/planning/2026-07-28-statsのリアクション数を概算に.md` にある。実装（`pg_class.reltuples` で概算する）と e2e テストは済んでいるが、統合に入っておらず（`main-統合.sh` の台帳で「作業中」）、本番には出ていない。この計画書は、残りの作業と、2026-11-12 に本番で分かったことをまとめる。

## 2026-11-12 に本番で起きたこと

- gamelore で、Tencent Cloud（AS132203）の 40 個の IP から、ヘッドレスのブラウザがトップページを繰り返し開いた。`POST /api/stats` が 14 時台に 557 回呼ばれ、**すべて 500（statement timeout、10 秒）**になった
- 1 回ごとに `note_reaction`（gamelore で約 4,500 万行）の全件 COUNT が 10 秒まで DB の CPU を使い続け、DB の load average が 4 コアで 11.8 に上がった。ほかの利用者の要求も遅くなり、「一瞬落ちた」ように見えた
- Cloudflare の WAF で止めたら戻った（honban-ops の `logs/2026-11-12-gameloreの14時台の遅延.md`）
- **キャッシュが効かない理由:** 今のコードは `count({ cache: 3600000 })` で 1 時間キャッシュするが、COUNT が statement timeout で失敗すると結果が保存されない。gamelore では COUNT が毎回 10 秒を超えるので、**キャッシュは一度も効かず、呼ばれるたびに全件 COUNT が実行される**。ふだんも 1 時間に 7〜17 件の stats のエラーが出ていた
- 外部から呼べる API が、呼ばれるたびに 10 秒の重いクエリを実行するので、DoS に使える状態である。概算に変える意味は大きい
