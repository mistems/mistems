# サーバーメトリクス収集の子プロセス廃止

ブランチ: `perf/server-stats-no-spawn`

## 背景

2026-11-08 に本番 (gamelore) の master プロセスの CPU プロファイルを取ったところ、`ServerStatsService` の 2 秒ごとの `tick` が master の CPU の 5.3% を使っていた。すべて systeminformation が起動する子プロセスによるもので、RSS が 1.5GB 前後ある master では fork 自体が重い。

| 呼び出し | 子プロセス | 割合 |
| --- | --- | --- |
| `si.networkInterfaceDefault()` | `execSync('ip route 2> /dev/null \| grep default')`。同期なので毎回イベントループが約 70ms 止まる | 2.4% |
| `si.networkStats(iface)` | `exec('cat /sys/class/net/<iface>/statistics/...')` | 1.5% |
| `si.disksIO()` | `exec('for mount in \`lsblk ... \| grep " disk " ...\`; do cat /sys/block/$mount/stat ...; done')` | 1.5% |

ウィジェット「サーバーメトリクス」(`serverStats` チャンネル) の表示内容・2 秒ごとの更新・値の意味は変えない。

## 方針

### 1. 既定のネットワークインターフェース名をキャッシュする

- Linux では `/proc/net/route` から既定経路 (Destination と Mask が 0、Flags に RTF_UP) のうち Metric が最小のインターフェースを選ぶ。見つからなければ systeminformation と同じく `os.networkInterfaces()` の外部インターフェース (scopeid が最小のもの、なければ最初のもの) を使う
- Linux 以外では `si.networkInterfaceDefault()` を使う
- 求められたら以後は使い回す。求められなかったら 60 秒あけて再試行する

### 2. ネットワークとディスクの統計を直接読む (Linux)

- ネットワーク: `/proc/net/dev` の該当インターフェースの受信バイト数・送信バイト数。`/sys/class/net/<iface>/statistics/{rx,tx}_bytes` と同じカーネルのカウンター (`dev_get_stats`) である
- ディスク: `/proc/diskstats` の「読み込み完了回数」「書き込み完了回数」。`/sys/block/<dev>/stat` の 1 列目・5 列目と同じ値である
- 毎秒の値は前回との差を経過時間で割って求める。最初の 1 回と、間が空いたあとの 1 回は 0 にする
- 値の意味:
  - `net.rx` / `net.tx`: systeminformation の `rx_sec` / `tx_sec` (バイト/秒)。差が負なら 0
  - `fs.r` / `fs.w`: `disksIO()` の `rIO_sec` / `wIO_sec` (読み書きの**回数**/秒)
- disksIO が数えるデバイスは「`lsblk` の TYPE が `disk` のもの」である。lsblk の判定 (util-linux の `get_type()`) に合わせ、`/sys/block` の各デバイスのうち次を除いたものを数える
  - `dm-*` (lvm・crypt など)、`loop*`、`md*` (raid)
  - major 番号が 1 のもの (RAM ディスク。lsblk が既定で除外する)
  - `device/type` の SCSI 種別が disk 以外のもの (5 = rom など)
  - パーティションは `/sys/block` の直下に現れないので、自然に除かれる
- デバイスの一覧は 5 分ごとに読み直す。合計の差ではなくデバイスごとの差を足すので、デバイスが増減しても値が跳ねない
- Linux 以外では今の systeminformation の処理を使う

### 3. 見ている人がいないときは収集を止める

- `serverStats` チャンネルは購読を始めたときと、その後 60 秒ごとに `ev` で `serverStatsWatching` を送る
- `ev` (xev) は cluster のプロセスをまたいで全プロセスに届くので、`ServerStatsService` がどのプロセスで動いていても合図を受け取れる
- `ServerStatsService` は最後の合図から 5 分たったら収集をやめる (タイマーは回し続け、tick の中で何もしない)
- 止めている間も `requestServerStatsLog` には答える。止まったあとに再開したときはログを空にしてから収集を始める (古い値を新しい値と並べない)

### 4. CPU とメモリ

- `osUtils.cpuUsage` は `os.cpus()` を 1 秒あけて 2 回読むだけで、子プロセスを起動しない
- `si.mem()` は Linux では `/proc/meminfo` を `fs.readFile` で読むだけで、子プロセスを起動しない
- どちらも変更しない

### 5. テスト

- `/proc` の解析と lsblk 相当の判定、毎秒の値の計算を `src/misc/linux-proc-stats.ts` の純粋な関数に分け、`test/unit/misc/linux-proc-stats.ts` で単体テストを書く

## 本番での確かめ方

- デプロイ後に master の CPU プロファイルを取り、`ServerStatsService` の tick の下に `spawn` / `execSync` / `ChildProcess` が現れないこと
- ウィジェットの NET・DISK の値がデプロイ前と同じくらいであること
- ウィジェットを閉じて 5 分以上たったあと、プロファイルに tick の処理が現れないこと

## 確かめた結果

OrbStack の Linux コンテナ (node:26.12.1-bookworm) で、`linux-proc-stats.ts` の関数と systeminformation 5.33.19 を同じタイミングで呼び比べた。

- 既定のインターフェース: どちらも `eth0` になった
- 数えるディスク: `lsblk | grep " disk "` の結果 (nbd0〜3, vda, vdb, vdc, zram0) と一致した
- 毎秒の値: 2 秒ごとに比べ、`rx_sec`・`tx_sec`・`rIO_sec`・`wIO_sec` がほぼ同じ値になった (systeminformation 側は前回の呼び出し時刻が数 ms ずれるので、完全には一致しない)
