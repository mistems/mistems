# ドライブ使用量集計の被覆インデックス計画

作成: 2026-11-08。ブランチ `index-optimize` に追加。

## 問題（調査済み・確定）

- **現象**: `DriveFileEntityService.calcDriveUsageOf` が発行する
  `SUM(size) WHERE "userId" = $1 AND "isLink" = FALSE` が、
  pg_stat_statements で **DB の合計時間 1 位**のクエリだった（gamelore 実測）
- **原因**: 既存の `IDX_drive_file_on_userId_and_isLink`
  （`("userId", "isLink")`、migration 1785227588654）で対象行は絞れるが、
  `size` を取るためにヒープを 1 行ずつ読む。ファイルの多い利用者ほどヒープの
  ランダム読みが増える

## 修正

`size` を INCLUDE した部分インデックスを 1 本追加する
（migration `1794126500691-drive-file-usage-covering-index.js`）:

```sql
CREATE INDEX "IDX_drive_file_userId_size_notlink"
    ON "drive_file" ("userId") INCLUDE ("size") WHERE "isLink" = false;
```

- 集計が index-only scan になり、ヒープを読まずに済む
- INCLUDE は TypeORM の `@Index` で表現できないため、エンティティ側は
  `@Index('IDX_drive_file_userId_size_notlink', { synchronize: false })` で名前だけ宣言し、
  **migration のみで管理**する（前例: 1785227588654 の
  `IDX_emoji_on_category_and_name_local`、`IDX_note_on_userId_and_channelId`）
- migration はブランチ既存の冪等ヘルパー流儀
  （CONCURRENTLY は `MISSKEY_MIGRATION_CREATE_INDEX_CONCURRENTLY=1`、
  INVALID 残骸の自動除去、**同名の有効なインデックスがあればスキップ**）

## 本番の状況

- gamelore-db2: 2026-11-08 に同名・同定義で手動作成済み（`CREATE INDEX CONCURRENTLY`）。
  ファイル 28,620 件の利用者で、読むバッファが 22,547 → 1,439、
  時間が 358ms → 118ms（コールド）になった。
  migration は有効な同名インデックスを見つけてスキップするため、作り直しは起きない
- systems-db1・favskey-db1: 未作成。migration で新規に作られる。
  ロックを避けるため `MISSKEY_MIGRATION_CREATE_INDEX_CONCURRENTLY=1` で migrate する

## 検証

- `pnpm --filter backend check-migrations` が 0 件で通る
- `pnpm migrate` → `pnpm revert` → `pnpm migrate` が通る
- デプロイ後、実クエリの EXPLAIN (ANALYZE, BUFFERS) で
  `Index Only Scan using IDX_drive_file_userId_size_notlink` になり、
  `Heap Fetches` が小さいこと（VACUUM 後は 0 に近づく）

## 備考

- 既存の `("userId", "isLink")` は今回のインデックスと役割が重なるが、
  `isLink = true` 側の検索や `userId` 単独の検索にも使われうるため残した。
  削除するかは pg_stat_user_indexes の `idx_scan` を見てから判断する
- `calcDriveUsageOfHost` / `calcDriveUsageOfLocal` / `calcDriveUsageOfRemote` は
  `userHost` で絞るため、このインデックスの対象外である
