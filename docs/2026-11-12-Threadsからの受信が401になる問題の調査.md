# Threads からの受信が 401 になる問題の調査

作成: 2026-11-12。まず調査。直すことになったら、ブランチ案 `fix/inbox-threads-signature`（最新の `origin/develop` から切る）。

## 本番で起きていること

- Threads（UA `facebookexternalua`）からの `POST /inbox` が、すべて 401 になっている。2026-11-12 の 0 時〜15 時で、gamelore 1,955 件、favskey 1,923 件（honban-ops の `logs/2026-11-12-アクセスログの点検.md`）。systems には来ていない
- journal には何も出ない（401 を返す前にログを書かない）
- 逆向き（こちらから Threads への配送）は、ときどき Threads 側が 500 を返すが、届いてはいる

## 401 を返す箇所

`packages/backend/src/server/ActivityPubServerService.ts` の `inbox()`:

```ts
try {
	signature = httpSignature.parseRequest(request.raw, { 'headers': ['(request-target)', 'host', 'date'], authorizationHeaderName: 'signature' });
} catch (_) {
	reply.code(401);
	return;
}
```

ここで 401 になるのは、`Signature` ヘッダーを解析できないか、必須のヘッダー（`(request-target)`・`host`・`date`）が署名に含まれていないときである。この後ろの 401（`host` を含まない、`digest` がないなど）も確かめる。

## 仮説

1. **Threads が RFC 9421（HTTP Message Signatures）の形式で署名している。** `Signature-Input: sig1=(...)` と `Signature: sig1=:base64:` の 2 つのヘッダーを使う形式で、Misskey が使っている draft-cavage 形式（`Signature: keyId="...",headers="...",signature="..."`）の解析器では読めない。Mastodon 4.4 以降は RFC 9421 の受信に対応しており、Threads も使っている可能性がある
2. 署名に `date` を含めていない（`created` だけを使うなど）
3. `Signature` ではなく `Authorization: Signature ...` で送っている

## 調べ方

1. **届いているヘッダーを見る。** 401 を返すときに、`facebookexternalua` からの要求について、署名に関係するヘッダー（`Signature`・`Signature-Input`・`Authorization` の有無と先頭、`Date`・`Digest`・`Content-Digest` の有無）を debug ログに出す。値の全体（署名そのもの）は出さなくてよい。署名は秘密ではないが、ログを短くするため
   - コードを変えずに見るなら、nginx のログに一時的に `$http_signature_input` などを出す方法もある（honban-ops 側。設定の変更なのでユーザーの承認が要る）。どちらで見るかはユーザーと決める
2. 仮説 1 なら、RFC 9421 の受信への対応を考える。本家（misskey-dev/misskey）に、RFC 9421 への対応の Issue や PR、既存のライブラリ（`@misskey-dev/node-http-message-signatures` など、本家が使っているもの）の対応状況があるかを確かめる。本家の依存に、すでに RFC 9421 を解析できるものが入っていれば、それを使う
3. 署名の鍵（`keyId`）の取得や、Threads のアクターの形式に特有の問題がないかも確かめる

## この調査の成果物

- 届いているヘッダーの形式と、401 の原因をこの計画書に書く
- 直し方の案（RFC 9421 の受信に対応する、など）と、その規模を書く。実装するかはユーザーと決める

## 2026-11-12 の調査（コードと公開情報から）

### 401 になる分かれ道

`inbox()` が 401 を返す箇所は 6 つある。前の 2 つは `@peertube/http-signature` の `parseRequest()` が例外を投げたときで、ライブラリのコード（`lib/parser.js`）から、次の場合に投げることを確かめた。

| # | 箇所 | 401 になる条件 |
|---|---|---|
| 1 | `parseRequest()` | `Signature` ヘッダーも `Authorization` ヘッダーもない |
| 2 | 〃 | `Signature` を draft-cavage の `keyId="...",algorithm="...",headers="...",signature="..."` として読めない。**RFC 9421 の `sig1=:...:` 形式はここで落ちる**（`bad param format` か `keyId was not specified`） |
| 3 | 〃 | `algorithm` がない（draft-cavage の hs2019 で `algorithm` を省く実装がある） |
| 4 | 〃 | `Date` が今と 300 秒より多くずれている（`clockSkew` の既定値） |
| 5 | 〃 | 署名した `headers` に `(request-target)`・`host`・`date` のどれかがない（`(created)` だけで `date` を署名しない実装はここで落ちる） |
| 6 | `parseRequest()` の後 | `Host` が `config.host` と違う、署名に `digest` がない、`Digest` ヘッダーがない・`SHA-256=` でない・本文と合わない。**RFC 9530 の `Content-Digest` だけを送る実装はここで落ちる** |

`Signature` が読めたあと、署名の検証そのもの（公開鍵での検証）は `InboxProcessorService` のジョブの中で行うので、401 にはならない。つまり今回の 401 は、署名の **形式**（ヘッダーの組み合わせ）で落ちている。

### 仮説の見直し

- Threads は 2024 年から Mastodon と連合している。Mastodon は 4.4 より前は draft-cavage しか検証できないので、Threads は少なくとも Mastodon 向けには draft-cavage で送っていると考えられる。ただし、相手によって形式を変えている（RFC 9421 を先に試す）可能性は残る
- Misskey（本家の develop も）は nodeinfo などで RFC 9421 に対応しているとは知らせていない（`grep` で確認）。相手の対応を見て形式を選ぶ実装なら、Misskey には draft-cavage を送るはずである
- したがって仮説 1（RFC 9421）だけでなく、表の 3・4・5・6（`algorithm` の省略、`Date` のずれ、`date` の代わりに `(created)`、`Digest` の代わりに `Content-Digest`）も同じくらいありうる。どれかは、届いているヘッダーを見ないと決められない
- 本家の develop は、受信の署名に `@peertube/http-signature` だけを使っている。本家が作った `@misskey-dev/node-http-message-signatures`（draft と RFC 9421 の両方を扱える）は、まだ backend の依存に入っていない

### 届いているヘッダーを見る方法（ユーザーと決める）

**案 B（推奨）: nginx のログに、Threads からの要求のヘッダーだけを一時的に出す。** コードを変えず、デプロイも要らないので、今日のうちに見られる。署名の値は秘密ではない。

```nginx
# http ブロック
map $http_user_agent $is_threads { ~*facebookexternalua 1; default 0; }
log_format inbox_sig '$time_iso8601 $status "$request" host="$http_host" date="$http_date" '
                     'sig="$http_signature" siginput="$http_signature_input" auth="$http_authorization" '
                     'digest="$http_digest" cdigest="$http_content_digest" ctype="$http_content_type"';

# 該当する server ブロック。既存の access_log の行は残し、その隣に足す
# (同じ階層に access_log を 1 行でも書くと、上の階層の access_log は引き継がれなくなるため)
access_log /var/log/nginx/inbox-sig.log inbox_sig if=$is_threads;
```

- 数分で数十件たまるので（1 日 2,000 件弱）、見たら設定を戻す
- `$time_iso8601` と `date` を比べれば、表の 4（時刻のずれ）も分かる
- honban-ops 側の作業で、設定の変更と nginx の reload が要るので、ユーザーの承認が要る

**案 A: Misskey のコードで、401 を返す箇所ごとに理由をログに出す。** どの分かれ道で落ちたかが直接分かるが、ブランチを作って統合し、デプロイするまで見られない。ログの出し方も考える必要がある（Threads からだけで 1 日 2,000 件弱あるので、UA で絞るか、間引く）。案 B で決めきれないときに使う。

### 原因ごとの直し方と規模（見積もり。AI が実装した場合の時間）

| 原因 | 直し方 | 規模 |
|---|---|---|
| RFC 9421（表の 2） | 受信で `Signature-Input` があれば RFC 9421 として読み、検証する。`@misskey-dev/node-http-message-signatures` を依存に足し、`inbox()` の解析、キューに渡す署名の型（`queue/types.ts`）、`InboxProcessorService` の検証を、draft と RFC 9421 の両方に対応させる。`Content-Digest` の検証も要る | 大。3〜4 ファイル、200〜400 行とテスト。2〜4 時間。本家が同じ対応を入れると衝突しやすい |
| `Content-Digest`（表の 6） | `Digest` がないとき `Content-Digest`（`sha-256=:base64:`）で本文を確かめる | 小。`inbox()` の数十行とテスト。30 分ほど |
| `(created)` で `date` がない（表の 5） | 必須ヘッダーの `date` を、`(created)` があれば省けるようにする | 小〜中。ライブラリの必須ヘッダーの指定を変え、`created` の期限を確かめる。1 時間ほど |
| `algorithm` がない（表の 3） | ライブラリが hs2019 の省略を受け付けないので、解析の前に補うか、ライブラリを替える | 中。1〜2 時間 |
| `Date` のずれ（表の 4） | Threads 側の問題。こちらで許容幅を広げるのは安全性とのかね合いなので、広げない | — |

どの原因でも、本家にも同じ問題がある（`inbox()` は本家と同じコード）。

## 2026-11-12 の決定と実装（案 A）

ユーザーの判断で、案 A（コードでログを出す）と案 B（nginx のログ。honban-ops のセッションが行う）を並行して進める。

### ログを debug に落とすブランチとの関係

ユーザーから「うるさいログを黙らせるブランチ（`annoy-logs-goneto-debuglevel`）で黙っているだけかもしれない」と指摘があったので確かめた。

- このブランチが変えたのは、`InboxProcessorService`・`QueueProcessorService`・`ApInboxService` など、**inbox が 202 を返したあとのジョブ処理** のログである（ジョブの失敗の詳細を debug に、`inbox activity ignored (maybe)` を warn から debug に）
- `ActivityPubServerService.inbox()` には触れていない。**401 の経路は、本家の時点でもともとログを 1 行も出していない**。黙っていたのはこのブランチのせいではない
- ただし、202 を返したあとに署名の検証で捨てられたもの（`inbox activity ignored`）は、このブランチで debug に落ちて見えなくなっている。今回の 401 とは別だが、Threads の調査で 202 になったあとに捨てられているものを見たいときは、このことに注意する

### 実装

- `inbox()` が 401 を返す 6 か所（`parseRequest` の例外、`host` を署名していない・一致しない、`digest` を署名していない、`Digest` がない・形式が違う・`SHA-256` でない・本文と合わない）で、理由を付けて `warn` で 1 行出す。ロガーは `ap-inbox`
- 出す内容: 理由（`parseRequest` の例外のメッセージを含む）、送り元のホスト（`keyId`、なければ `actor` から）、UA、`Signature` の形式（`cavage` か、それ以外か）、`Signature-Input`・`Authorization` の有無、`keyId`、`algorithm`、署名したヘッダーの一覧、`Digest`・`Content-Digest` のアルゴリズム名、`Date`、要求の `Host`。**署名の値と本文のハッシュの値は出さない**
- 間引き: 送り元のホストと理由の組ごとに、10 分に 1 回だけ出す。次に出すときに、間引いた件数を `(suppressed N same rejections)` として添える。記録は 1,000 組を超えたら捨てる
- レベルは `warn`。本番の既定は `info` 以上を出すので見える。`annoy-logs-goneto-debuglevel` の対象にもならない
- 401 を返す挙動そのものは変えていない

出力の例（e2e で確かめたもの）:

```
inbox rejected (401): reason="parseRequest: bad param format" from=remote.example ua="node-fetch" signature=other signatureInput=yes authorization=no keyId="https://remote.example/users/1#main-key" algorithm=- signedHeaders="\"@method\" \"@target-uri\" \"content-digest\"" digest=no contentDigest="sha-256" date=- requestHost="127.0.0.1:61812"
```

### テスト

- unit（`test/unit/misc/inbox-reject-log.ts`、8 件）: `keyId` の取り出し（draft-cavage・RFC 9421）、要約に署名の値が入らないこと、間引き
- e2e（`test/e2e/fetch-resource.ts`）: 署名のない POST と RFC 9421 の形式の POST が 401 になること。`fetch-resource.ts` の 86 件すべてが成功した
- テストの環境では `NODE_ENV=test` でログがすべて黙るので、一度だけ `env.ts` の黙らせる行を外して実行し、上の例のとおりログが出ることを確かめた（戻してある）

## 原因（2026-11-12、案 B の nginx のログで判明）

honban-ops のセッションが、gamelore で 15:15〜15:20 に Threads からの要求 15 件のヘッダーを記録した（honban-ops の `logs/2026-11-12-Threadsの署名ヘッダーの記録/`）。

- 署名の形式は、202 も 401 も同じ draft-cavage だった。`keyId="https://threads.net/ap/users/<id>/#main-key"`、`algorithm="rsa-sha256"`、`headers="(request-target) host date digest"`。`Signature-Input`・`Content-Digest`・`Authorization` はない。**RFC 9421 ではなかった**
- 受け取った時刻と `Date` の差は、202 が 2〜260 秒（10 件）、401 が 347〜558 秒（5 件）。**300 秒できれいに分かれる**
- つまり表の 4（`Date` のずれ）だった。Threads は配送を待たせても、最初に付けた `Date` のまま送ってくると考えられる
- `parseRequest()` に `clockSkew` を渡しておらず、ライブラリの既定値 300 秒で、ずれを絶対値で検査していた（`@peertube/http-signature` の `lib/parser.js` で確かめた）
- 受け付けたあとの `InboxProcessorService` の `httpSignature.verifySignature()` は署名の検証だけで、時刻は検査していない（`lib/verify.js` で確かめた）。時刻の検査は `parseRequest()` の 1 か所だけである

上の表の「`Date` のずれ: Threads 側の問題なので広げない」という判断は、この結果を見て改めた。Mastodon が受け付ける要求を Misskey だけが弾いており、相互運用の問題だからである。

## 修正

- `parseRequest()` に `clockSkew: 3600`（前後 1 時間）を渡す
- Mastodon の許容幅（`app/lib/signed_request.rb` の `SignedRequest#matches_time_window?` で確かめた）:
  - `expires` のない普通の署名では、過去は `Date` から 5 分＋`CLOCK_SKEW_MARGIN`（1 時間）＝ **65 分まで**、未来は **1 時間まで**
  - `EXPIRATION_WINDOW_LIMIT = 12.hours` は、署名に `expires` を付けたときの上限で、`Date` だけの署名には効かない
- ライブラリの `clockSkew` は過去と未来の両方に同じ幅を使うので、Mastodon の未来の幅に合わせた 1 時間にした。過去は Mastodon より 5 分短いが、観測した遅れ（最大 558 秒）には十分である
- リプレイについて: 盗み見た署名付きの要求を送り直せる時間が 5 分から 1 時間に延びる。ただし配送は TLS の上を流れ、署名は `(request-target) host date digest` に結び付いているので、ほかのサーバーや別の本文には使えない。Mastodon と同じ幅なので、連合の相手として新しい弱さは生まない
- 401 の理由のログは、案 A で入れたものをそのまま残した。`Date` で弾いたときは `reason="parseRequest: clock skew of 3700.123s was greater than 3600s"` のように出る

### テスト

- e2e（`fetch-resource.ts`）に 3 件足した。形式・`Host`・`Digest` をそろえた draft-cavage の要求で、`Date` が 10 分前なら 202、2 時間前と 2 時間後なら 401。修正前は「10 分前」が 401 で失敗し（本番と同じ）、修正後は `fetch-resource.ts` の 89 件すべてが成功した

## デプロイ後に確かめること（honban-ops 側）

- nginx のログで、`facebookexternalua` の `POST /inbox` の 401 が消える（残るなら、1 時間を超えて遅れた要求か、別の原因）
- journal の `inbox rejected (401)` に、Threads から何が出るか
- nginx の一時的なログ設定を戻す
