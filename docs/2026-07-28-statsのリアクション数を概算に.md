# /api/stats の note_reaction 全件カウントを概算値に置き換える計画

作成: 2026-07-28。ブランチ `perf/stats-reaction-count-estimate`（origin/develop 直系）。

## 背景（調査済み）

- gamelore の Papertrail 監視中、`[api] Internal error ... in stats: ...
  statement timeout` が短時間に大量発生しているのを発見（別件のタイムライン
  DB フォールバック調査から派生）
- 原因は `packages/backend/src/server/api/endpoints/stats.ts` の
  `this.noteReactionsRepository.count({ cache: 3600000 })`。1時間キャッシュが
  切れるたびに `note_reaction` の**全件 COUNT** が走る
- `note_reaction` は3台とも数百万〜数千万行の巨大テーブルと判明:
  - gamelore: **44,519,141 行**
  - favskey: 3,466,432 行
  - systems: 16,003,866 行
  （調査当初、gamelore は `n_live_tup` の統計が壊れていて実測「6,700行」に
  見えていたが、これは統計側の不具合で誤り。ANALYZE 実行後に正しい値が判明）
- gamelore で実測: `EXPLAIN (ANALYZE, BUFFERS) SELECT COUNT(1) FROM
  note_reaction` は **Parallel Seq Scan、Execution Time 10,325ms**
  （ANALYZE で統計を修正した後の値。修正前は統計乖離のせいでプランが
  さらに悪く、31,592ms〜57,358ms を観測）
- ANALYZE で統計は直ったが、**「4,500万行の全件 COUNT」という処理自体が
  本質的に重い**ため、これ以上はクエリの設計を変えるしかない
- upstream develop には `enableEnhancedServerStats` というフラグで
  この COUNT をスキップ可能にするコミット (`c0efad6ee3`, 2024-11) が
  存在するが、**現在デプロイ中の環境にはまだ反映されていない**
  (`meta` テーブルに `enableEnhancedServerStats` カラム自体が無いことを
  3台で確認済み)。今回はこのフラグに乗る形ではなく、正確な値を
  概算で安く出す方向で対応する

## 2026-11-12 の本番の障害（追記）

詳しくは同じブランチの `docs/planning/2026-11-12-statsのリアクション数概算の仕上げ.md`。要点をここにも書く。

- gamelore で、Tencent Cloud（AS132203）の 40 個の IP から、ヘッドレスのブラウザがトップページを繰り返し開いた。`POST /api/stats` が 14 時台に 557 回呼ばれ、すべて 500（statement timeout、10 秒）になった
- 1 回ごとに `note_reaction`（約 4,500 万行）の全件 COUNT が 10 秒まで DB の CPU を使い続け、DB の load average が 4 コアで 11.8 に上がった。ほかの利用者の要求も遅くなった。Cloudflare の WAF で止めて回復した
- **1 時間のキャッシュが効かない理由:** `count({ cache: 3600000 })` は、クエリが成功したときにだけ結果をキャッシュに書く。gamelore では COUNT が毎回 statement timeout（10 秒）で失敗するので、キャッシュに一度も書かれず、呼ばれるたびに全件 COUNT が実行される。ふだんも 1 時間に 7〜17 件の stats のエラーが出ていた
- つまり、認証なしで呼べる API が呼ばれるたびに 10 秒の重いクエリを実行する状態で、DoS に使える。概算に変えると、`pg_class` を 1 行読むだけになる

## 対象と方針

- 対象ファイル: `packages/backend/src/server/api/endpoints/stats.ts` のみ
- `this.noteReactionsRepository.count({ cache: 3600000 })` を、
  `pg_class.reltuples`（ANALYZE 時にサンプリングされる推定行数）を使った
  概算取得に置き換える
- **前例が Misskey 本体に既にある**:
  `packages/backend/src/server/api/endpoints/admin/get-table-stats.ts` が
  `DI.db`（`DataSource`）を注入し、`this.db.query(\`SELECT ... reltuples
  ...\`)` で `pg_class` を直接読んでいる。今回もこのパターンを踏襲する
  （TypeORM の QueryBuilder は `pg_class` のようなシステムカタログを
  対象にできない/する意味がないため、この1点だけ生クエリになるのは
  正攻法。詳細は get-table-stats.ts 参照）

  他の作業ブランチ（fanout-timeline 系、index-optimize 等）はこのファイルを

## 実装方針（詳細）

### 変更前

```ts
constructor(
    @Inject(DI.instancesRepository)
    private instancesRepository: InstancesRepository,

    @Inject(DI.noteReactionsRepository)
    private noteReactionsRepository: NoteReactionsRepository,

    private notesChart: NotesChart,
    private usersChart: UsersChart,
) {
    super(meta, paramDef, async () => {
        // ...
        const [reactionsCount, instances] = await Promise.all([
            this.noteReactionsRepository.count({ cache: 3600000 }),
            this.instancesRepository.count({ cache: 3600000 }),
        ]);
        // ...
    });
}
```

### 変更後（案）

- `@Inject(DI.db) private db: DataSource` を追加
- `noteReactionsRepository.count()` を以下相当の概算取得に置き換え:

  ```ts
  private async estimateRowCount(tableName: string): Promise<number> {
      const rows = await this.db.query(
          'SELECT reltuples::bigint AS estimate FROM pg_class WHERE relname = $1',
          [tableName],
      );
      return Number(rows[0]?.estimate ?? 0);
  }
  ```

  呼び出し側: `this.estimateRowCount('note_reaction')`
- `instancesRepository.count()` は変更しない（3台とも1万〜1.5万行程度で
  COUNT 自体軽い。スコープ外）
- `cache: 3600000` オプションは概算取得には不要（`pg_class` の読み出し自体が
  一瞬なので、TypeORM 側のキャッシュ機構を挟む意味がない。素直に毎回
  `db.query()` する）

### 精度についての注意（正直に書く）

- `reltuples` は ANALYZE/autovacuum 実行時点のサンプリング値であり、
  リアルタイムの正確な行数ではない
- ANALYZE 直後は実測とほぼ一致するが、以後 INSERT/DELETE が進むと徐々に
  ズレる。autovacuum が正常に機能していれば大きくは狂わない
  （今回3台とも ANALYZE 実行済み、かつ本計画のもう一つの成果として
  autovacuum の統計乖離問題自体を解消済み — 別途 `postgres-optimization-plan.md`
  等に記録する想定）
- `/api/stats` は「だいたいの規模感を見せる」用途のエンドポイントであり、
  admin/get-table-stats.ts も同じ理由で reltuples 概算を採用している。
  今回の変更はこの前例と整合する

## 検証（デプロイ後）

- 3台で `/api/stats` のレスポンスタイムが1秒未満になっていること
- Papertrail で `"Internal error" "in stats"` の
  `QueryFailedError ... statement timeout` が消えること
- 返る `reactionsCount` が実際の行数と大きくズレていないこと
  （ANALYZE 直後の実測値と比較。数値の性質上、完全一致は保証しない）

## テスト

- 型・返り値の形は変わらない（`reactionsCount: number`）ので、
  既存の e2e テストがあれば regression として維持されることを確認
- 新規: `/api/stats` を叩いて `reactionsCount` が `number` かつ `0` 以上で
  あることを確認するテスト（統計値の厳密一致はテストできないため、
  型と非負であることの確認に留める）

## スコープ外

- `instancesRepository.count()` — 現状 1〜1.5万行程度で COUNT 自体軽いため
  対象外
- `enableEnhancedServerStats` フラグの導入・upstream 追従 — 別件。
  今回は「値は出しつつ安くする」方向で対応するため、フラグでスキップする
  設計とは別軸
- favskey/systems の autovacuum・統計問題そのものへの追加対応 — 既に
  ANALYZE で解消済み（本計画は「解消後もなお重い COUNT(*) 設計」への対処）
