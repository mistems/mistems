## 2. 連合に要る条件と、Misskey のコードが要求すること

### 2.1 HTTPS と NODE_ENV

Misskey の連合の制約は、多くが `NODE_ENV === 'production'` のときだけ効く。

- **http の URL**: `checkHttps()` は、`NODE_ENV` が `production` でなければ `http://` も通す [確認] `packages/backend/src/misc/check-https.ts`。リモートのノート・ユーザー・画像の取り込みがこれを使う (`ApNoteService.ts`、`ApPersonService.ts`、`ApImageService.ts`)
- **private IP の遮断 (SSRF 対策)**: 接続先の IP が private なら切るのは `NODE_ENV === 'production'` のときだけで、`allowedPrivateNetworks` に入れた範囲は除く [確認] `packages/backend/src/core/HttpRequestService.ts` の `isPrivateIp`
- **WebFinger**: `@user@host` の形で引くときは `https://<host>/.well-known/webfinger` を使う。環境変数 `MISSKEY_WEBFINGER_USE_HTTP=true` で http になる。URL (`http://…/@user`) で引くときはその URL のスキームを使う [確認] `packages/backend/src/core/WebfingerService.ts` の `genUrl`
- **取得した結果の URL の確認**: https で頼んだのに http の結果が来ると拒否する。http どうしなら通る [確認] `packages/backend/src/core/activitypub/misc/check-against-url.ts`
- 開発モード (`pnpm dev`) は `NODE_ENV` を設定しない [確認] `scripts/dev.mjs` に `NODE_ENV` の記述がない。したがって開発モードどうしなら、http・private IP のままで連合できる見込みである [推測]。本番モード (`--prod`、`NODE_ENV=production`) では http の相手を拒否するので、検証環境の枠 (`http://devN.localhost:3080/`) は本番モードでは連合できない

### 2.2 ホスト名の解決と、相手から見た URL の一致

ActivityPub では、ノートやユーザーの ID は `url` から作った絶対 URL である。相手のサーバーは、その URL をそのまま引いて取りに来る。したがって、**それぞれのサーバーの `url` のホスト名が、相手のコンテナの中から同じ名前で引けて、同じサーバーに届く**ことが要る。

検証環境の枠では、ここが詰まる。

- 枠の `url` は `http://devN.localhost:3080/` で、ブラウザは `*.localhost` を 127.0.0.1 に向けてホストの Caddy に届く [文書] 検証環境の計画書「全体の構成」
- web コンテナでは `extra_hosts` で自分の `devN.localhost` だけを 127.0.0.1 に向ける (実装計画 Task 3 の `slot_entries`)。**相手の `devM.localhost` をコンテナの中からどう引くかは決まっていない**。Debian 系の Node のイメージ (glibc) が `*.localhost` を特別扱いするかは確かめていない [推測] が、どちらにしても 127.0.0.1 (自分) か解決できないかのどちらかになり、相手には届かない
- ホストの Caddy は `127.0.0.1:3080` に公開している。コンテナから `host.docker.internal` で Mac に届くことは文書にある [文書] [OrbStack docs: Container networking](https://docs.orbstack.dev/docker/network) が、Mac の 127.0.0.1 だけで待ち受けているポートに届くかは文書に書かれていない (未確認)

### 2.3 OrbStack の HTTPS と名前解決 (裏取りした事実)

- コンテナのドメインに対し、OrbStack は設定なしで HTTPS を用意する。証明書はドメインごとにその場で作り、逆プロキシで終端する [文書] [OrbStack docs: Domains](https://docs.orbstack.dev/docker/domains)、[OrbStack 1.1 のお知らせ](https://orbstack.dev/blog/orbstack-1.1-https)
- 独自ドメイン (`dev.orbstack.domains` ラベル) とワイルドカードにも HTTPS が効く。独自ドメインは `.local` に限られる [文書] 同上
- OrbStack はルート CA をコンテナに入れるので、コンテナどうしでも `orb.local` のドメインを証明書の検証を切らずに使える。ラベル `dev.orbstack.add-ca-certificates=false` で止められる [文書] [OrbStack docs: HTTPS](https://docs.orbstack.dev/features/https)
- コンテナの中の CA のパスは `/usr/local/share/ca-certificates/orbstack-root.crt` で、Node はそのままでは読まない (OpenSSL のストアを使わせるか、証明書のファイルを指定する) という報告がある [文書・第三者] [Arcjet の記事](https://arcjet.com/learn/secure-local-dev-servers-orbstack)。Misskey なら `NODE_EXTRA_CA_CERTS` に同じファイルを渡せば足りる見込みである [推測] (test-federation も同じ方法で自前の CA を渡している [確認] `packages/backend/test-federation/.config/example.docker.env`)
- コンテナのドメインは「コンテナのドメインと IP へのアクセスを許可」(Settings → Network) に依存する [文書] Domains のページ
- 独自ドメインがほかのコンテナとホストの両方から引けることは、検証環境の計画の中で 2026-11-12 に確かめてある [文書] 検証環境の計画書「全体の構成」
- OrbStack のコンテナの IP は `192.168.x.x` / `fd07:…` の private IP である [確認] claudeImplement の `orb-dev.sh` の `write_default_yml` のコメント。今の `orb-dev.sh` は `allowedPrivateNetworks` に `127.0.0.0/8`・`192.168.0.0/16`・`172.16.0.0/12`・`fd00::/8` を入れている

## 3. 構成の候補

### 案 A: 上流の test-federation を OrbStack でそのまま動かす

`packages/backend/test-federation/` は、`a.test` と `b.test` の 2 台の Misskey、それぞれの nginx (TLS 終端) と PostgreSQL、共用の Redis、テストを動かす `tester` を compose で立てる [確認] `compose.yml`・`compose.a.yml`・`compose.b.yml`・`compose.override.yaml`。

- `setup.sh` が自前のルート CA と `a.test`・`b.test` の証明書を作り、Misskey には `NODE_EXTRA_CA_CERTS` で渡す。Misskey は `NODE_ENV=production` で `url: https://a.test/` のまま動き、`allowedPrivateNetworks` に nginx のいる `172.20.0.0/16` を入れる [確認] `setup.sh`、`.config/example.default.yml`、`compose.tpl.yml`
- 名前の解決は compose のサービス名 (`a.test` など) で行う。ホストにポートを公開しない [確認] compose のどのファイルにも `ports:` がない
- テストは vitest で、`test/*.test.ts` を `pnpm -F backend test:fed` で動かす。`resolveRemoteUser` / `resolveRemoteNote` / `WAIT_FOR_FEDERATION` などの道具がそろっている [確認] `test/utils.ts`
- Misskey はホストの `pnpm build` の成果物 (`built/`、`packages/*/built`) を bind mount して動く [確認] `compose.tpl.yml`

| 利点 | 難点 |
| --- | --- |
| 本番モード・https・SSRF 対策を有効にしたままで、実運用に近い条件で確かめられる | ブラウザで画面を見られない (`https://a.test/` を Mac から引けず、`/etc/hosts` の書き換えは要 sudo) |
| ホストにポートを公開しないので、OrbStack の方針とぶつからない。上流の CI と同じものを動かすので、作る量がいちばん少ない | 事前に `pnpm build` が要る。起動に時間がかかる |
| 計画書 §6・§9 が予定している「test-federation に足す」をそのまま実行できる。テストとして残るので、上流の更新のたびに回せる | サブネット (`172.20`〜`172.23.0.0/16`) と compose のプロジェクト名 (ディレクトリ名 `test-federation`) が固定で、2 つのワークツリーで同時に動かせない |
| | リレーがない (F8 には工夫が要る、§4.3) |

### 案 B: 検証環境の枠を 2 つ立てて互いに連合させる

自ブランチの環境 (例: dev1) と、相手役の環境 (例: dev2) を開発モードで立て、`http://dev1.localhost:3080/` と `http://dev2.localhost:3080/` で連合させる。相手役には `origin/develop` のワークツリー (= 本家 Misskey) を使える。

| 利点 | 難点 |
| --- | --- |
| 両方の画面をブラウザで見られる。`*.localhost` なので Claude が `admin` でログインして確かめ、スクリーンショットを撮れる (F12) | §2.2 のとおり、コンテナから相手の `devM.localhost` に届かない。検証環境の計画に足すものが要る (§6) |
| 相手を本家 Misskey (origin/develop) にでき、「受信側に何も配らない」前提 (R4) をそのまま確かめられる | http・開発モードでしか連合できない。本番モードの条件 (https、SSRF 対策) は確かめられない |
| seed のデータや HMR をそのまま使える | ホスト名にポートが入る (`dev1.localhost:3080`)。相手からは `@admin@dev1.localhost:3080` になる。ポート付きのホストで崩れる箇所がないかは確かめていない [推測] |
| | 枠を替えると、相手の DB に残った `dev1.localhost:3080` のユーザーと食い違う (§7) |

### 案 C: Mastodon を相手にする

Mastodon の公式イメージ (web・sidekiq・streaming と PostgreSQL・Redis) を compose で立てる。

| 利点 | 難点 |
| --- | --- |
| F13 (非 Misskey の相手で public に見えるか、付記の URL が content で読めるか) を確かめられるのはこれだけ | Mastodon は本番の設定で https を前提にするので、両方の Misskey も https にする必要がある [推測]。OrbStack の HTTPS (独自ドメイン `*.local`) に乗せることになり、枠の `*.localhost` とは別の名前になる |
| | Mastodon にも private IP への接続を許す設定が要る [推測] (`ALLOWED_PRIVATE_ADDRESSES`。未確認) |
| | 立てる量が多く、Mastodon の更新を追う手間が増える。`*.local` では Claude がテスト用の認証情報を画面に入力できない (API とトークンで操作することになる) |

### 案 D: リレーを立てる

YUKIMOCHI Activity-Relay や aode-relay などの実際のリレーを compose に足す。

| 利点 | 難点 |
| --- | --- |
| F8 を本物の経路 (Follow → Accept → 配送) で確かめられる | リレーも https と自分のドメインを要する [推測]。Misskey は Accept を送ってきたアクターの inbox がリレーの inbox と一致するかを見るので [確認] `packages/backend/src/core/RelayService.ts` の `updateRequestingRelayStatus`、偽物では通らない |
| | F8 のためだけに立てるには重い。§4.3 の代わりの方法で足りる見込み |

### 判断

- **自動のテスト (F1〜F10) は案 A**。本番に近い条件で確かめられ、テストとして残る。足すのはテストのファイル 1 本と、OrbStack で動かすための手順だけである
- **画面の確認 (F12) と、F11 は案 B**。検証環境の計画に「枠どうしの名前解決」を足して実現する
- **案 C (Mastodon) は今回は見送る**。付記の URL は content にも入っていて、Mastodon が public のノートを公開として扱うのは既知の挙動なので、F13 は案 A・B の結果と Mastodon の仕様から推して足りるとみる。どうしても要るなら、OrbStack の HTTPS を使う別の compose として後で足す (§7)
- **案 D は立てない**。F8 は案 A の中で、相手の Misskey の inbox をリレーとして登録する方法 (§4.3) で確かめる

### 4.2 動かし方 (OrbStack)

ホストにポートを公開しないので、OrbStack でもそのまま動く見込みである [推測]。ワークツリーの間でぶつからないように、compose のプロジェクト名を分ける。

```bash
cd /Users/riin/workspace/misskey-worktrees/feat/channel-federation
pnpm build                       # ホストで実行する (CLAUDE.md が禁じているのはホストの pnpm dev だけ)
cd packages/backend/test-federation
bash ./setup.sh                  # 初回だけ。certificates/ と .config/*.yml を作る (.gitignore 済み)
export NODE_VERSION="$(cat ../../../.node-version)" COMPOSE_PROJECT_NAME=fed-channel-federation
docker compose up -d --scale tester=0 --wait     # a.test / b.test が healthy になるまで待つ
docker compose run --no-deps --rm tester -- pnpm -F backend test:fed packages/backend/test-federation/test/channel.test.ts
docker compose down              # volumes/ は bind mount なので、作り直すときは volumes/ を消す
```

- サブネットが固定なので、**同時に動かせる test-federation は 1 組だけ**である。別のワークツリーで動かすときは、先に `down` する。`docker network ls` で `172.2x` を使う別のネットワークが無いことを確かめる
- テストでは自前の CA を使うので、OrbStack の HTTPS は使わない。`a.test` などの名前は compose のネットワークの中だけで引ける
- ホストで `pnpm build` しない場合は、GitHub Actions の `Test (federation)` を `workflow_dispatch` で riin で動かす手もある [確認] `.github/workflows/test-federation.yml` の `on:` に `workflow_dispatch` がある。ただし riin で Actions を動かせるかは確かめていない

## 5. 推奨案 2: 検証環境の枠どうしを連合させる (画面の確認)

### 5.1 構成

```
dev1 (feat/channel-federation、開発モード)        dev2 (origin/develop = 本家 Misskey、開発モード)
  url: http://dev1.localhost:3080/                   url: http://dev2.localhost:3080/
  web コンテナ                                        web コンテナ
   ├ /etc/hosts: dev1.localhost → 127.0.0.1           ├ /etc/hosts: dev2.localhost → 127.0.0.1
   └ 共有ネットワーク orb-dev-slots                    └ 共有ネットワーク orb-dev-slots
       別名 dev1.localhost  ◀── AP (http) ──▶  別名 dev2.localhost
ブラウザ → http://devN.localhost:3080/ → ホストの Caddy → devN.mistems-slot.local:3080 (今の計画のまま)
```

- 枠を取った web コンテナを、外部の docker ネットワーク `orb-dev-slots` にもつなぎ、`aliases: [devN.localhost]` を付ける。dev1 のコンテナから `http://dev2.localhost:3080/` を引くと、docker の内蔵 DNS が dev2 の web コンテナの IP を返し、dev2 の Misskey (コンテナの中で 3080 番で待ち受け) に直接届く [推測]
- 自分の名前は `extra_hosts` (`/etc/hosts`) が先に効くので 127.0.0.1 のまま [推測: glibc の既定の nsswitch は files が先]
- Caddy を経由しないので、Caddy の設定は変えなくてよい。`127.0.0.1` に公開したポートにコンテナから届くかという未確認の点 (§2.2) も避けられる
- 別名の重複は枠の台帳が防ぐ (同じ枠を持つ環境は 1 つだけ)。止まっているコンテナの別名は内蔵 DNS に出ない [推測]
- web コンテナに `MISSKEY_WEBFINGER_USE_HTTP=true` を渡す。`@admin@dev2.localhost:3080` の形で引くときに http で WebFinger を引くため (§2.1)

### 5.2 手順の案

## 6. 検証環境の計画やスキルに足すべきこと

検証環境の計画 (claudeImplement) の完了後に、別の小さな計画として足す想定である。今の計画の作業には混ぜない。

1. **枠どうしの名前解決 (`--fed`、または枠の既定の動き)**: 枠を取った web コンテナを外部ネットワーク `orb-dev-slots` につなぎ、別名 `devN.localhost` を付ける。ネットワークは `ensure_proxy` と同じ場所で、無ければ作る。`slot_entries` に `networks:` を足すことになる。害がなければ `--fed` を設けず、枠を取った環境の既定にしてもよい (連合しない環境でも、別名が増えるだけである)
2. **`MISSKEY_WEBFINGER_USE_HTTP=true`**: 枠の環境の web に渡す。連合しないときは影響しない
3. **枠を替えたときの連合相手との食い違いの警告**: `rewrite-url.sql` は自分の DB の自分のオリジンを書き換えるが、**相手の DB に残った `user.host = 'dev1.localhost:3080'` などは書き換えない** (ホストの列にはスキームが無く、そもそも別の DB である)。枠を替えると、相手は「同じホストの別の鍵のサーバー」を見ることになり、署名の検証が通らなくなる [推測]。`up` で枠が替わるとき、DB に `host LIKE 'dev%.localhost:%'` のユーザーがいれば、「枠どうしで連合した環境は `--slot` で同じ枠に固定するか、`down -v` で作り直す」と警告する
4. **SKILL.md の追記**: 「枠どうしの連合は開発モードだけで動く (本番モードは http を拒否する)」「相手役に本家 Misskey が要るなら origin/develop のワークツリーを立てる」「連合の自動テストは test-federation を使う」と、§5.2 の手順を短く書く
5. **test-federation の動かし方**: スキルにするほどではないが、`orb-dev-server` の SKILL.md か `working-on-backend` に §4.2 の手順 (プロジェクト名を分ける、同時に 1 組だけ) を書いておくと、次の連合の機能でも使える
