# リモートノートのリアクションの同期

作成日: 2026-10-25
ブランチ: `feat/remote-note-refetch`（PR: fruitriin/misskey#57）

## 目的

リレーなどで流れてきたリモートのノートについて、届いた後に付いたリアクションを、元のサーバーの画面を開かなくても、自分のサーバーで見られるようにする。

## 今の動きと、目的に届かない理由（2026-10-25 に gamelore で確認）

- ノートの詳細ページで「再取得」を押すと、`notes/refetch` が再取得のジョブを積み、`ApNoteService.updateNoteIfStale` が ActivityPub の Note を取り直す
- 例: gamelore の `asq39a3cvl`（元は `https://misskey.systems/notes/asq39a3cb0`）は、再取得に成功した（`refetchedCount = 1`）。しかし gamelore 側のリアクションは `{}` のままで、元のノートには `:owa_desuwa@.:` が 2 件付いていた
- Misskey の ActivityPub の Note には、リアクションの情報が無い（`@context`、`attachment`、`attributedTo`、`cc`、`content`、`id`、`inReplyTo`、`published`、`sensitive`、`tag`、`to`、`type` だけである）
- リアクションは、付けたときに `Like` として作者のサーバーへ送られるだけで、リレーで受け取った側には届かない。ActivityPub では取りようがない

## 方針

相手が Misskey 系のサーバーのときだけ、相手の公開 API を読んでリアクションを同期する。

- 対象: `instance.softwareName` が Misskey 系（misskey、sharkey、cherrypick、firefish、iceshrimp、foundkey など。一覧は定数にする）で、ノートの `uri` が `https://<host>/notes/<id>` の形のもの
- 呼ぶ API: `POST https://<host>/api/notes/show`（`{ noteId }`、認証なし）
- 同期するタイミング: 再取得（`updateNoteIfStale`）が成功した直後。TTL（4 時間）とホストごとの上限（1 時間 30 回）は、再取得と同じものを使う。API を呼ぶ回数も上限に数える
- 失敗しても、再取得そのものは成功として扱う（リアクションの同期だけを諦める）。失敗の理由は `warn` でログに残す

### 段階

- **第 1 段階（この計画）**: リアクションの種類と数、リアクションのカスタム絵文字を同期する
- **第 2 段階（同じブランチで続けて行う。2026-10-25 にユーザーが決定）**: 誰が付けたか（`notes/reactions`）を取り込み、リモートのユーザーを解決して `note_reaction` を作る

## 第 1 段階の設計

### リアクションの名前の変換

相手の `reactions` のキーを、自分のサーバーでの名前に変える。

| 相手のキー | 自分のサーバーでのキー |
| --- | --- |
| Unicode の絵文字（`👍`） | そのまま |
| `:name@.:`（相手のサーバーのカスタム絵文字） | `:name@<相手のホスト>:` |
| `:name@other.host:`（第三のサーバーのカスタム絵文字） | そのまま |
| `:name@<自分のホスト>:`（自分のサーバーのカスタム絵文字） | `:name:`（DB 上の形。表示のときに `:name@.:` になる） |

変換は純粋な関数に切り出して、単体テストを書く。

### 数の決め方

- キーごとに、`max(自分のサーバーの数, 相手の数)` を取る
  - 相手の数には、自分のサーバーの利用者が付けたリアクションも含まれる（Like が相手に届くため）。基本は相手の数が正しい
  - 相手にまだ届いていない自分の側のリアクションを、消さないために max にする
- 自分のサーバーにしか無いキーは残す
- `note.reactions` を更新する。`note_reaction` の行は作らない（第 1 段階では、誰が付けたかは分からない）

### カスタム絵文字

- 変換後に `:name@host:` になるものは、自分のサーバーの `emoji` テーブルに、そのホストの絵文字として無ければ登録する
  - 画像の URL は、その絵文字のホスト自身の `POST /api/emoji`（`{ name }`）で取る。リクエストはそのホストの上限に数える
  - 相手の `reactionEmojis` に書かれた第三のホストの URL は使わない。絵文字は (name, host) でサーバー全体に共有されるので、相手が嘘の URL を返すと第三のホストの絵文字を差し替えられてしまう（2026-10-25 のセキュリティレビューの指摘）
  - 第三のホストが Misskey 系でないとき、または上限に当たったときは登録せず、数だけを反映する
  - 既にある (name, host) の絵文字は上書きしない
- 登録は、既存のリモート絵文字の登録処理（`ApNoteService` の `extractEmojis` が使っているもの）と同じ形にする

### 画面への反映

- 更新後は、今の再取得と同じく `publishNoteStream(noteId, 'updated')` を出す。開いている画面は `notes/show` を取り直して、新しいリアクションを表示する
- ノートのキャッシュがあれば消す

## 第 2 段階の設計（誰が付けたか）

2026-10-25 のユーザーの判断: 知らないユーザーの解決は、リレーで Like を受け取ったときにも普段から行っている処理なので、普段の活動の範疇とみなす。人数の上限は付けない。

### 取り込み方

- 相手の `POST /api/notes/reactions`（`{ noteId, limit: 100, untilId }`、認証なし）を、空になるか 100 件未満になるまでページングして読む
- 付けたユーザーは、相手の返す `user` の `username` と `host`（null なら相手のホスト）で決める
  - 自分のサーバーに既にいるユーザーは、DB から引くだけにする（`RemoteUserResolveService.resolveUser` は 24 時間より古いユーザーを取り直すので、通信を増やさないため）
  - いないユーザーは `RemoteUserResolveService.resolveUser` で解決する（Like を受け取ったときと同じく、WebFinger と Person の取得を行う）
  - 自分のサーバーのローカルユーザーは取り込まない。ローカルのユーザーのリアクションは自分のサーバーが正であり、相手に残っているのは Undo の配送の失敗などで古くなったものだからである
- `note_reaction` は `ReactionService.create` で作る。Like を受け取ったときと同じ処理を通すので、ブロック、公開範囲、リノート、リアクションを受け付けない設定（`reactionAcceptance`）、使えない絵文字、メディアをサイレンスしたホストなどは同じように弾かれる（`❤` への置き換えを含む）
  - リモートのユーザーのリアクションなので、配送はしない（`ReactionService.create` は、付けたユーザーがローカルのときだけ配送する）。ノートの作者もリモートなので、通知も作らない
  - 凍結されたユーザー、連合が禁止されたホストのユーザーは取り込まない（Like を受け取ったときも、凍結された actor の activity は捨てる）
  - 既に (userId, noteId) の行があるユーザーは何もしない（別のリアクションへの置き換えもしない）

### 数の整合

- `ReactionService.create` は数を 1 増やす。第 1 段階で数を相手の数に合わせているので、そのままでは二重に数えてしまう
- そこで、取り込みで増やした分（作った行のリアクションごとの件数）を、取り込みの後でまとめて引き戻す。増減はどちらも SQL の加減算なので、同時に届いた Like の加算は失わない
- 最後に、キーごとに `GREATEST(自分の数, 相手の数, note_reaction の行の数)` にする
- リアクションのバッファリング（`enableReactionsBuffering`）が有効なときは、Redis にあるまだ書き込まれていない差分を、相手の数から引いてから比べる（後で書き込まれる分を二重に数えないため）

### 上限

- `notes/reactions` の 1 ページごとに、相手のホストの上限（1 時間 30 回）を 1 回使う
- 知らないユーザーの解決 1 人ごとに、そのユーザーのホストの上限を 1 回使う
- 上限に当たったら取り込みをそこで止め、残りは数だけの反映で済ませる

### 第 2 段階のテスト

- 単体テスト: 二重に作らない（既に行があるユーザーは `create` を呼ばない）、数が二重にならない（増やした分を引き戻す）、上限で止まる、ローカルのユーザー・凍結されたユーザーは取り込まない
- 開発環境: `asq39a3cb0` で、リアクションを付けたユーザーが、ノートの「リアクション」タブに出ること
