# チャンネル連合 ハッシュタグでつなぐ

作成日: 2026-11-13

[チャンネル連合の計画書](2026-08-01-チャンネル連合.md) の続きである。連合するチャンネル (`federationPolicy: 'public'`) のノートに、チャンネルごとのハッシュタグを自動で付けて送り出す。あわせて、外から届いた同じハッシュタグのノートを、そのチャンネルに収蔵できるようにする。

本文では、ソースを読んで確かめたことには **[確認]** とファイルパスを、手元で試して確かめたことには **[試験]** を、まだ確かめていない見込みには **[推測]** を付ける。

## 1. ねらい

今は、連合するチャンネルのノートの本文の末尾に `From: 「チャンネル名」 <URL>` を付けて送っている [確認] `packages/backend/src/core/activitypub/ApRendererService.ts`。この URL は、相手のユーザーがチャンネル単位でワードミュートするための目印も兼ねている。ただ、URL によるミュートは Misskey どうしでないと扱いにくく、相手からチャンネルに加わる方法もリプライしかない。

ハッシュタグは Mastodon などでも検索・フォロー・フィルタの対象になる。チャンネルにハッシュタグを付ければ、次のことができる。

- 相手のユーザーが、そのハッシュタグを付けて投稿すれば、チャンネルに加われる (収蔵が有効なとき)
- 相手のユーザーが、ハッシュタグの文字列でワードミュートできる

ただし、相手のサーバーのトレンドを荒らさないことを優先する (§3、§5.2)。そのため、相手のサーバーでハッシュタグとして数えられる形では送らない。ハッシュタグをフォローしてチャンネルを購読する使い方は、あきらめる

## 2. ハッシュタグの名前

形は `#連合チャンネル_{チャンネル名}` とする。例: `#連合チャンネル_雑談`。「連合チャンネル_」が入るので、たまたま同じハッシュタグを使う人とぶつかることは、まずない。

**サーバー名は入れない** (2026-11-13 変更。はじめは `#{サーバー名}連合チャンネル_{チャンネル名}` だった)。ほかのサーバーに同じ名前の連合するチャンネルがあれば、ハッシュタグが同じになり、互いのノートを収蔵しあえる (§4)。この機能を持つほかのサーバーのチャンネルを、そのまま自分のサーバーのチャンネルの画面で読み書きできる。

### 2.1 使える文字

MFM では、次のようにハッシュタグとして読まれた [試験] `mfm-js` の `parse`。

| 書いたもの | ハッシュタグとして読まれた部分 |
| --- | --- |
| `#gamelore.example連合チャンネル_雑談` | `gamelore` (「.」で切れる) |
| `#連合チャンネル_A B` | `連合チャンネル_A` (空白で切れる) |
| `#連合チャンネル_「雑談」` | 全体 (かぎ括弧は通る) |
| `#連合チャンネル_雑談・告知` | 全体 (中黒は通る) |

- Mastodon のハッシュタグは、文字・数字・下線などしか使えない見込みである [推測]。かぎ括弧や中黒は、Mastodon ではハッシュタグの途中で切れるおそれがある。そこで、**チャンネル名から、文字・数字・下線以外を取り除く**。取り除いた結果が空になるチャンネル名 (記号だけの名前など) は、チャンネルの ID の末尾を代わりに使う
- 長さは、Misskey のハッシュタグの上限 (128 文字) に収める [確認] `packages/backend/src/models/Hashtag.ts`。長いチャンネル名は切り詰める

### 2.2 チャンネル名を変えたとき

チャンネル名からその都度ハッシュタグを作ると、名前を変えたときにハッシュタグも変わり、相手のフォローやミュートが外れてしまう。そこで、**連合を有効にしたときにハッシュタグを決めて、チャンネルに保存する** (`channel.federationHashtag`)。名前を変えてもハッシュタグは変わらない。

- チャンネルの持ち主は、編集画面でハッシュタグを変えられる。このサーバーのほかのチャンネルと同じハッシュタグにはできない。ほかのサーバーのチャンネルと合わせたいときは、ここで同じハッシュタグに変える
- ハッシュタグを変えると、相手のフォローやミュートが外れることを、確認のダイアログで知らせる

## 3. 出ていく側: 本文の付記にハッシュタグの文字列を書く

- 連合するチャンネルのノートを AP で送るとき、本文の末尾の付記に、チャンネルのハッシュタグを書く。例: `From: 「雑談」 #連合チャンネル_雑談 <URL>`。URL はチャンネルへのリンクとして残す
- **ノートの `tag` (AP の Hashtag) には入れない**。リモートの Misskey は、ノートのハッシュタグを `tag` の配列からだけ取り込み、本文の「#…」からは取り込まない [確認] `packages/backend/src/core/activitypub/models/tag.ts` の `extractApHashtags`、`NoteCreateService.ts` の `apHashtags` (`tag` がなければ空の配列になり、本文からは抜き出さない)。Mastodon も `tag` の配列から取り込む見込みである [推測]。そのため、相手のサーバーでは、ハッシュタグのページにもトレンドにも数えられない
  - 相手が Misskey なら、本文の MFM の「#…」はハッシュタグのリンクとして表示される (押すと相手のサーバーのハッシュタグのページに飛ぶが、そのノート自体はそこに出ない) [推測]。Mastodon では、`tag` にないハッシュタグはリンクにならず、ただの文字として表示される見込み [推測]
- **ローカルのノートの `tags` にも入れない**。送り出すときに付記に書くだけにする。こうすると、自分のサーバーのトレンドやハッシュタグのページにも、チャンネルのノートが混ざらない
- 相手のユーザーが、自分の投稿にこのハッシュタグを付けて (相手のサーバーで `tag` に入る形で) 投稿するのは、相手のユーザーの意思による。そのぶん相手のトレンドに数えられるのは、ふつうのハッシュタグの使い方と変わらない

## 4. 入ってくる側: 同じハッシュタグのノートを収蔵する

- 設定は設けず、**連合するチャンネルは常に収蔵する** (2026-11-13 決定)。連合しないチャンネル (`federationPolicy: 'none'`) は収蔵しない
- 連合するチャンネルに、そのチャンネルのハッシュタグがある**リモートの公開のノート**が届いたら、そのノートをチャンネルに入れる (`channelId` を付ける)
- ハッシュタグは、AP の `tag` と本文の両方から探す。本文からは「連合チャンネル_」を含むハッシュタグだけを拾う。§3 のとおり、この機能を持つサーバーどうしではチャンネルのハッシュタグを `tag` に入れず付記に書くので、本文を見ないと、ほかのサーバーの同じ名前のチャンネルのノートを収蔵できない。本文から拾ったハッシュタグは収蔵の判定にだけ使い、ノートの `tags` には入れない
- 収蔵しないもの
  - 公開以外のノート (ホーム・フォロワー限定・ダイレクト)
  - ローカルのユーザーがチャンネルの外でハッシュタグを手で付けたノート (チャンネルに投稿してもらう)
  - 連合しないチャンネルのハッシュタグのノート
- このサーバーに届くリモートのノートは、ローカルのだれかがフォローしているユーザーのものか、リレーで届いたものだけである。**外で付いたハッシュタグのノートが全部集まるわけではない**ので、設定の説明にそう書く
- 荒らし対策
  - チャンネルの持ち主とモデレーターが、収蔵したノートをチャンネルから外せるようにする (ノートは消さず、`channelId` だけを外す)
  - サーバーのブロックやサイレンスは、今までどおり効く

## 5. ハッシュタグのトレンドへの影響

### 5.1 自分のサーバーのトレンド

トレンドは、ハッシュタグごとに 10 分の区切りで、使ったユーザーの数を数えている [確認] `packages/backend/src/core/HashtagService.ts` の `updateHashtagsRanking`。リモートのノートも、公開とホームなら数える [確認] `packages/backend/src/core/NoteCreateService.ts` の「ハッシュタグ更新」。

- 自分のチャンネルのノートは、§3 のとおりローカルの `tags` に入れないので、トレンドには入らない
- 外から届いた、チャンネルのハッシュタグの付いたノートは、そのままでは数えられる。そこで、**`連合チャンネル_` を含むハッシュタグはトレンドの集計から外す**。今の除外は、管理画面の「非表示のハッシュタグ」と完全に一致したものだけなので [確認] `updateHashtagsRanking` の `hiddenTags`、ここに名前の形で外す条件を足す。ほかのサーバーが同じ形を真似したハッシュタグも外れる

### 5.2 相手のサーバーのトレンド

相手のトレンドは、こちらからは止められない。`tag` に入れて送ると、相手が Misskey ならユーザーの数で数えられ、チャンネルに投稿する人が多いほど上がる。ハッシュタグにチャンネル名が入っているので、宣伝のように見えて、お行儀がよくない。

そこで §3 のとおり、**`tag` には入れず、本文の付記に文字列として書くだけにする**。相手のサーバーのハッシュタグのページにもトレンドにも、こちらから送ったノートは数えられない。相手のトレンドに出るのは、相手のユーザーが自分でこのハッシュタグを付けて投稿したぶんだけになる。

この形でも、相手のトレンドに出るかは連合テストで確かめる (§7)

## 9. 進み具合と結果 (2026-11-13)

段階 1〜4 をすべて実装した。§6 の表の段階 1 の「ハッシュタグを付ける」の設定と、段階 2 の「AP の `tag` に足す」は、§8 の決定 (付記は選べない、`tag` には入れない) に合わせて実装していない。

### 段階 1: ハッシュタグの保存

- migration `1794500774672-channel-federation-hashtag` で、`channel` に `federationHashtag` (varchar(128)、nullable) と `federationHashtagNormalized` (varchar(128)、nullable、一意のインデックス) を足した
- 重なりの判定は、Misskey のハッシュタグと同じ `normalizeTag` (NFKC + 小文字化) で正規化した値で行う。正規化した値を別の列に持ち、一意のインデックスを張った。式のインデックス (`lower(normalize(...))`) は TypeORM の entity で表せず、`check-migrations` と食い違うためである。この列は、外から届いたノートのハッシュタグを照合するとき (段階 4) の検索にも使う
- 名前の作り方は `packages/backend/src/misc/channel-federation-hashtag.ts` の `buildChannelFederationHashtag`、重なりを避ける処理は `ChannelFederationHashtagService.generate` にある。`_2`、`_3` を付けるときも、全体が 128 文字 (コードポイントで数える) に収まるようにチャンネル名を切り詰める。サーバー名がとても長いときは、チャンネル名を 6 文字残してサーバー名も切り詰める
- `channels/create` と `channels/update` で連合を 'public' にしたとき、まだハッシュタグがなければ作って保存する。'none' に戻しても消さない。チャンネル名を変えても変わらない
- `channels/update` の `federationHashtag` で、持ち主 (とモデレーター) が付け替えられる。先頭の「#」は取り除く。誤りのエラーコードは、使えない文字 `INVALID_FEDERATION_HASHTAG`、長すぎる `FEDERATION_HASHTAG_TOO_LONG`、ほかと重なる `FEDERATION_HASHTAG_ALREADY_USED` に分けた
- **付け替えるハッシュタグには「連合チャンネル_」を必須にした** (`FEDERATION_HASHTAG_MUST_CONTAIN_MARKER`)。目印がないと、§5.1 のトレンドの除外が効かず、`#cats` のようなよく使われるハッシュタグにすると関係のない外のノートまでチャンネルに収蔵してしまうためである
- packed の Channel に `federationHashtag` を足した
- 編集画面: 連合が「連合する」のとき、ハッシュタグの欄を出す。まだ決まっていないとき (今回連合にする場合) は、欄を無効にして「保存すると自動で決まる」と表示する。変えて保存するときは、相手のミュートやフォローが効かなくなることを確認のダイアログで知らせる

### 段階 2: 出ていく側

- `ApRendererService.renderNote` の付記を `From: 「チャンネル名」 #ハッシュタグ URL` にした。AP の `tag` にもローカルの `note.tags` にも入れない
- **チャンネルのノートには、必ず `_misskey_content` (MFM の原文) を付けるようにした**。本文が素の文字だけのノートは、これまで HTML (`content`) だけを送っていた。HTML だけだと、`tag` に無いハッシュタグのリンク (`<a rel="tag">`) は、相手の Misskey で `[#…](https://a.test/tags/…)` というただのリンクに変わることが連合テストでわかった [試験]。MFM の原文を送れば、相手の Misskey では相手のサーバーのハッシュタグのリンクとして表示され、`tags` には入らない
- 連合テストで、b.test に届いたノートの本文に付記のハッシュタグがあり、`tags` が空で、`notes/search-by-tag` に出ないことを確かめた [試験]

### 段階 3: トレンドの除外

- `HashtagService.updateHashtagsRanking` で、「連合チャンネル_」を含むハッシュタグ (正規化したもの) を数えない
- e2e と連合テストで、同じノートに付けたふつうのハッシュタグはトレンドに出て、チャンネルのハッシュタグは出ないことを確かめた [試験]

### 段階 4: 収蔵

- `NoteCreateService.create` の最後のほう (連合の方針を当てたあと) で、次の条件をすべて満たすノートを、ハッシュタグが一致するチャンネルに入れる
  - リモートのユーザーのノート
  - チャンネルがまだ決まっていない (リプライでチャンネルに入る経路が優先)
  - 公開で `localOnly` でない (サイレンスで home に降格したものは入らない)
  - `apHashtags` (AP の `tag`) に、連合する (`federationPolicy: 'public'`、アーカイブされていない) チャンネルのハッシュタグがある (正規化して比べる)
  - 中身のないリノートではない
- チャンネルに入ったノートは、DB でも Redis のチャンネルのタイムラインでも、チャンネルのノートとして扱われる (既存の `pushToTl` のチャンネルの分岐を通る)
- `channels/remove-note` を足した。チャンネルの持ち主とモデレーターが、リモートのノートの `channelId` を null にする。ノートは消さない。ローカルのノートは外せない (外すと連合しないチャンネルの `localOnly` のノートがローカルタイムラインなどに出るため)。`notesCount` を 1 減らし、Redis の `channelTimeline`、`userTimelineWithChannel`、チャンネルをフォローしている人の `homeTimeline` / `homeTimelineWithFiles` から外す
- ノートのメニューの「チャンネル」の中に「チャンネルから外す」を足した。持ち主かモデレーターで、ノートがリモートのものときだけ出る
- 連合テストで、b.test のユーザーが公開でハッシュタグを付けて投稿すると a.test のチャンネルのタイムラインに入り、外すと消えること、ホーム・フォロワー限定と連合しないチャンネルのハッシュタグでは入らないことを確かめた [試験]

### わかったこと・残っていること

- **収蔵したノートは、そのユーザーをフォローしているローカルの人のホームタイムラインに出なくなる**。チャンネルのノートは、ホームタイムラインではチャンネルをフォローしている人にだけ出るためである (リプライでチャンネルに入るノートも、もとから同じ)。連合テストでも、収蔵されたノートは alice (投稿者をフォローしている) のホームに届かなかった [試験]。気になるようなら、収蔵したリモートのノートをフォロワーのホームにも流すかを、別に決める
  - **§11 で対応した**。フォロワーのホームにも出し、タイムラインのオプションで出さないようにもできる
- チャンネルから外したノートは、Redis の `userTimeline` には足し直さない (古いノートを足すと並びが崩れるため)。ユーザーのページでは DB からの補充で出る [推測]
- Mastodon でのハッシュタグの扱い (§7) は確かめていない

## 10. サーバー名を外した (2026-11-13)

ハッシュタグを `#連合チャンネル_{チャンネル名}` にし、サーバー名を入れないようにした。ほかのサーバーの同じ名前の連合するチャンネルと、互いのノートを収蔵しあうためである。

- `buildChannelFederationHashtag` は、チャンネル名と ID だけから作る。`ChannelFederationHashtagService` は、サーバーの表示名とドメインを使わなくなった
- 重なりの判定 (`_2`、`_3` を付ける) は、今までどおりこのサーバーの中だけで行う。このサーバーに同じ名前のチャンネルが 2 つあると、2 つめは `_2` が付き、ほかのサーバーの同じ名前のチャンネルとはつながらない。つなげたいときは、持ち主が編集画面でハッシュタグを合わせる
- 収蔵 (`NoteCreateService.collectIntoFederatedChannelByHashtag`) は、AP の `tag` に加えて、本文から「連合チャンネル_」を含むハッシュタグを拾って照合する (`extractChannelFederationHashtagsFromText`)。この機能を持つサーバーどうしでは `tag` にハッシュタグが入らないためである。ノートの `tags` には入れないので、トレンドとハッシュタグのページには響かない
- 連合テストの H1 を、a.test と b.test に同じ名前の連合するチャンネルを作り、互いのノートが相手のチャンネルに入ることの確認に置き換えた
- migration は変えていない (列の形は同じで、作り方だけが変わった)。開発の環境で、すでにサーバー名入りのハッシュタグが保存されているチャンネルは、そのまま残る

## 11. 収蔵したノートを投稿者のフォロワーのホームにも出す (2026-11-13)

§9 の「わかったこと」の 1 点目に対応した。チャンネルに入ったリモートのノート (ハッシュタグで収蔵したもの、リプライでチャンネルに入ったもの) を、投稿者をフォローしているローカルの人のホームとソーシャルにも出す。タイムラインのオプションで、出さないようにもできる。

### 対象

- `channelId` があり、投稿者がリモートのユーザー (`userHost` が null でない) のノート
- 閲覧者が投稿者をフォローしていて、そのチャンネルをフォローしていないとき。チャンネルをフォローしていれば、今までどおりオプションと関係なく出る
- 既定は「出す」にした。収蔵の機能ができる前は、これらのノートはフォロワーのホームに出ていたので、それを保つ
- ミュートしているチャンネルのノートは、今までどおり出さない

### 実装

- 配る側: `NoteCreateService.pushToTl` のチャンネルの分岐で、投稿者がリモートなら、チャンネルのフォロワーに加えて、投稿者のローカルのフォロワー (`isFollowerHibernated: false`) の `homeTimeline` / `homeTimelineWithFiles` にも入れる。リプライは、チャンネルでないノートと同じく `withReplies` で選ぶ。チャンネルのフォロワーと重なる人には二重に入れない
- 読む側: `notes/timeline` と `notes/hybrid-timeline` に `withCollectedChannelNotes` (boolean、既定 true) を足した
  - Redis から読む経路: false のとき、フォローしていないチャンネルに入ったリモートのノートを `noteFilter` で除く。今は投稿者のフォロワーの homeTimeline に入っているためである
  - DB から読む経路 (`getFromDb`): true のとき、「`channelId` があり、`userHost` があり、投稿者をフォローしている」ノートを OR で足す。ミュートしているチャンネルのノートと、ミュートしているチャンネルのノートのリノートは除く
- ストリーミング: `homeTimeline` と `hybridTimeline` のチャンネルの init の引数に `withCollectedChannelNotes` (既定 true) を足した。true なら、フォローしていないチャンネルのノートでも、投稿者がリモートで閲覧者がフォローしていれば流す
- フロントエンド: タイムラインのオプション (ホームの「…」メニュー) に「チャンネルに収蔵されたノートを表示」を足した。ホームとソーシャルのときだけ出す。保存先は `withRenotes` などと同じ `store` の `tl.filter.withCollectedChannelNotes` で、この項目ができる前に保存した設定は true として扱う。デッキのタイムラインのカラムのメニューにも、ホームとソーシャルのときだけ足した (カラムごとに保存する)
- misskey-js を再生成した。ストリーミングの型 (`streaming.types.ts`) にも引数を足した

### 結果

- e2e (`test/e2e/channel-federation.ts`): `enableFanoutTimeline` の true と false の両方で、DB の上でリモートのユーザーのチャンネルのノートに書き換えたノートが、投稿者のフォロワーの `notes/timeline` と `notes/hybrid-timeline` に既定では出て、false では出ないこと、チャンネルをフォローしていれば false でも出ること、チャンネルをミュートしていれば出ないこと、投稿者をフォローしていない人には出ないことを確かめた [試験]
- 連合テスト H7: b.test の bob が a.test のチャンネル (alice はフォローしていない) のハッシュタグを付けて投稿すると、チャンネルに収蔵され、bob をフォローしている alice の `notes/timeline` と `notes/hybrid-timeline` に既定では出て、`withCollectedChannelNotes: false` では出ないこと、bob をフォローしていない carol のホームには出ないことを確かめた [試験]。連合テストの環境は fanout timeline が有効なので、`pushToTl` で配った分を確かめたことになる
- ストリーミングの分岐は、試験を足していない [推測]

### 残っていること

- `channels/remove-note` は、チャンネルのフォロワーの homeTimeline からノートを外す。チャンネルのフォロワーが投稿者もフォローしているときは、外したあとのノート (チャンネルに属さなくなる) もその人のホームに出るはずだが、Redis からは消える。DB からの補充では出る [推測]
