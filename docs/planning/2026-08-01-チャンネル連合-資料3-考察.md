# 考察: フォーク実装比較を踏まえたチャンネル連合設計の再検討

成果物 3/3。[資料1 当初計画](2026-08-01-チャンネル連合-資料1-当初計画.md) の計画と [資料2 フォーク比較](2026-08-01-チャンネル連合-資料2-フォーク比較.md) の比較結果を突き合わせ、計画をどう修正すべきか、何が本質的に難しいままなのかを考察する。

## 1. 比較が明らかにした設計空間の構造

2 つの実在フォークと本家ドラフトは、偶然にも設計空間の 3 つの頂点をきれいに張っている。

- **Type4ny**: 「チャンネル所属」をプロトコルから捨てる。連合は最小コストで手に入るが、リモート側にとってチャンネルは存在しない。
- **yojo-art**: 「チャンネル = Actor」に全振りする。購読・配送・発見・ピン留めまで連合するが、可視性の細やかさ (localOnly、オプトイン) をフォークの方針ごと捨てて成立している。
- **本家ドラフト (#289)**: Actor は置くが、力点は語彙とモデレーション意味論 (isSensitive の home 降格、silence/suspend の効果、allowRenoteToExternal の受信側義務)。配送方式は規定しない。

01-plan の案 B (unlisted + `_misskey_channel`) はこの三角形の内点であり、「タイムライン避けの意味論を連合先でも保存する」という要求に最も忠実なのは依然として案 B である。ただし比較を経て、案 B 単独では弱いことも明確になった。以下で理由を述べる。

## 2. yojo-art から採り入れるべき知見

### 2.1 「チャンネルアカウント = 隠しユーザー」は実装コストの正解

計画時点 (01-plan §3 案 C) では Actor 化を「鍵ペア、inbox/outbox、WebFinger の追加実装が必要な大工事」と見積もっていた。yojo-art の実装はこの見積りが過大だったことを示している。**チャンネルに 1:1 で紐づくローカルユーザーを作ってしまえば、AP に必要な機構は全部ついてくる**。migration 1 本 (channel.host / channel.actorId / user.channelId) と `SignupService` の拡張で Actor は立つ。

さらに副産物が大きい:

- チャンネルフォローが `following` テーブルに統合され、**チャンネルフォローの連合 (リモートユーザーによるチャンネル購読) が Follow の既存実装だけで動く**
- モデレーションも既存機構に乗る: リモートチャンネルが荒れたら、その Actor をユーザーとして silence / suspend すればよい。これは本家ドラフトが規定する「システムユーザーへの silence/suspend の効果」と同型で、ドラフトの思想と Actor 実装が噛み合うことの傍証になっている
- `attributedTo` によるオーナー表現、featured コレクションによるピン留め連合も無料で手に入る

一方で対価も確認できた。ユーザー名名前空間をチャンネルと共有すること (衝突・スクワッティング)、「ログインしないユーザー」がユーザー一覧・検索・統計に漏れ出ないようにする例外処理、そして user と channel の 1:1 参照が壊れた時の整合性である。yojo-art はこれらを `isBot` + `user.channelId` 判定の散在で処理しており、修正コミットが続いている (v1.8.1, v1.9.0)。採用するなら「チャンネルアカウントを通常ユーザーから隔離する述語」を最初に一元化すべきである。

### 2.2 「@メンション互換レイヤー」は graceful degradation を超える発明

計画の R4 (graceful degradation) は「非対応実装で壊れないこと」までしか要求していなかった。yojo-art の本文先頭への `@channel@host` 挿入は、それを超えて**非対応実装からの参加 (graceful participation) を実現している**。Mastodon ユーザーが Group アカウントにメンションを付けるだけでチャンネルに投稿でき、受信判定もメンションに一本化されるため、対応・非対応が混在するネットワークで壊れにくい。

これは Guppe (グループボット) が実証してきた「メンション駆動グループ」のパターンを Misskey のチャンネルに接いだものと解釈でき、枯れたパターンの流用という意味でも筋が良い。

ただし裏面として「**単に Group アカウントに言及しただけのノートが意図せずチャンネル投稿になる**」問題 (最初に発見されたチャンネルに入れる仕様) を抱える。話題として `@channel` を引用しただけの投稿がチャンネル TL に流入し得る。ここは `audience` プロパティ (yojo-art は書くのに読んでいない) を**受信側でも一次判定に使い、メンションはフォールバックに格下げする**ことで大幅に緩和できる。「audience があればそれに従う。なければメンションから推定する」という 2 段判定が、標準への忠実さと互換性を両立する改善案である。

### 2.3 Announce 方式の落とし穴も実物が教えてくれた

yojo-art では Note の Update / Delete がチャンネルフォロワーに届かない (投稿者のフォロワーへの配送しか行われない)。これは Group-Announce 方式 (FEP-1b12) の構造的な弱点で、**Create だけ Announce しても、その後のライフサイクルイベントを Group が中継しなければ購読者のビューは腐る**。FEP-1b12 が Update/Delete も Group が Announce することを求めているのはこのためである。自前実装するなら「チャンネル経由で配送されるアクティビティの種類」を最初に列挙し、Create 以外 (Update / Delete / 投票 / リアクション?) をどこまで中継するか決めてから書くべき、という教訓になる。

同様に、リモートチャンネル宛投稿の LD-Signature 依存 (チャンネルホストによる転送を受信側が検証できるようにする) も注意点である。LD-Signature は本家でも受信フォールバックとして残ってはいるが将来性が不透明で、FEP-8b32 (Object Integrity Proofs) への移行が業界的な流れになっている。転送を前提にする設計は、転送検証の技術選定を独立の論点として持つ。

## 3. 本計画 (案 B) 側で維持すべき判断

比較の結果、逆に yojo-art / Type4ny に**追随すべきでない**点も明確になった。

1. **オプトイン既定は譲れない。** Type4ny は既定で連合 (オプトアウト)、yojo-art は全チャンネル連合である。どちらも「チャンネル = 連合しない場」という既存ユーザーの前提を破壊している。既存チャンネルに投稿してきた人の期待を守るには、チャンネル単位のオプトイン (R5) + 連合状態の常時表示が必要である。これは本家 #14048 の合意方向 (デフォルト localOnly 維持) とも一致する。
2. **localOnly の廃止には付き合わない。** yojo-art の設計は「localOnly を認めない」というフォーク方針の上に成立しており、可視性強制の削除を安全にしている。localOnly を残す本計画 (と本家系フォーク一般) では、チャンネルの連合設定とノート単位の localOnly の直交性を保つ必要がある (01-plan Phase 1 の設計どおり)。
3. **「リモート側でのタイムライン避け」は本計画だけが扱っている。** Type4ny は public 送出でリモート GTL に載る。yojo-art も public 投稿は非対応実装の GTL に載る (対応実装同士なら channelId が付いて除外される)。unlisted (AP 上 home) 送出は、**未対応実装に対してもタイムライン避けを保つ唯一の手段**であり、「サーバー内全員に見せたくない投稿をリモートとやりとりする」という当初の動機に直結する。維持すべきである。なお yojo-art がチャンネル投稿に home 可視性を許していることから、Group-Announce と unlisted の組み合わせに実装上の障害がないことも確認できた (Announce 対象は public/home)。

## 4. 計画の修正: Actor を Phase 3 から前倒しする

当初計画は「Phase 1: メタデータ付き unlisted 連合 → Phase 3: Actor 化」の順だったが、比較を踏まえると**チャンネル Actor の作成だけは Phase 1 に前倒しすべき**である。理由は 3 つ。

1. **ワイヤ形式のネットワーク効果。** yojo-art 方式 (Group Actor + cc/メンション + Announce) は 2026 年 7 月から実網で動いている。`audience` に入れる URI が「解決すると Group Actor が返る URI」であれば、yojo-art 系サーバーはこちらのチャンネルをリモートチャンネルとして自動認識でき、購読までできる。URI が解決不能なままだと、この相互運用は一切発生しない。
2. **実装コストの再見積り。** §2.1 のとおり、Actor を立てるコスト自体は当初見積りより大幅に小さい (migration 1 本 + SignupService 拡張)。高コストなのは Actor ではなく「リモートチャンネルの受信表現」と「Announce 中継の完全性」の側である。
3. **tesaguri 氏の段階案との一致。** 「まず inbox を持つ Group としてチャンネル情報を連合し、Note の audience でそれを指す。配送 (Announce) は後から足す」という順序は、Discussion #14049 で本家側にも提示されている経路であり、将来の本家実装と収斂しやすい。

修正後のロードマップ:

| Phase | 内容 | 当初計画からの変更 |
|---|---|---|
| 0 | migration: channel.federationPolicy + **channel.actorId / user.channelId** | Actor 用カラムを前倒し追加 |
| 1 | 連合チャンネルに Group Actor を生成 (署名可能・Follow 受付可)。ノートは unlisted 送出 + `audience`(= Actor URI) + `_misskey_channel` + **@メンション互換挿入** | Actor 生成と互換メンションを前倒し |
| 2 | 受信: `audience` 一次判定 + メンション フォールバックで channelId 解決。リプライ還流の整理。リモート Group の MiChannel 化 (閲覧のみ) | audience を読む点が yojo-art と異なる |
| 3 | チャンネル Actor による Announce 配送 (Create に加え **Update / Delete も中継**)。リモートチャンネルへの投稿 (転送署名は FEP-8b32 を第一候補に検討) | 中継対象の明示、署名技術の選定を追加 |
| 4 | モデレーション連合: `_misskey_channel` の isSensitive / allowRenoteToExternal を送受信し、本家ドラフトの受信側義務 (home 降格・リノート抑止) を実装 | ドラフト仕様の受信側を明示的に採用 |

こうすると各 Phase の互換相手が明確になる: Phase 1 完了で「非対応実装に unlisted ノート + メンションとして見える」、Phase 2 完了で「yojo-art からの投稿を受けられる」、Phase 3 完了で「yojo-art と対等に相互購読できる」、Phase 4 で「本家が #289 系で実装してきた場合に整合する」。

## 5. それでも残る本質的な課題

1. **標準の分裂リスク。** yojo-art (Group + メンション + Announce)、本家ドラフト (Application + `_misskey_channel`)、FEP-1b12 (Group + audience + Announce) は互いに少しずつずれている。本考察の提案は「Actor type は Group、所属表現は audience 優先 + `_misskey_channel` 併記 + メンション互換」という全部乗せで橋を架ける構えだが、本家が別形式で実装した場合の追随コストはゼロにならない。語彙・判定ロジックを 1 モジュールに閉じ込め、差し替え可能にしておくことが唯一の保険である。
2. **スコープ保証は結局「紳士協定」である。** unlisted も allowRenoteToExternal も、受信側実装が尊重して初めて意味を持つ。連合した瞬間に、そのノートは技術的には公開情報になる (公開 URL で取得でき、悪意ある実装は何でもできる)。UI では「連合チャンネル = サーバー外に出ても構わない投稿の場」であることを明示し、「見られたくない」ではなく「積極的に見せて回らない」が保証の上限であることをユーザーに伝えるべきである。これは可視性 followers/specified が既に抱えるのと同じ性質だが、「チャンネル = 閉じた場」という既存のメンタルモデルがある分、誤解の余地が大きい。
3. **リモートチャンネルのモデレーション非対称。** 本家 #14048 が挙げるとおり、リモートチャンネル (自サーバーに管理者がいない場) からの流入には専用のモデレーション操作 (チャンネル単位サイレンス・連合カット) が要る。Actor 方式なら既存のユーザーモデレーションが流用できる (§2.1) が、「ユーザーの silence」と「チャンネルの silence」を運用者が同一視してよいかは UI 設計の問題として残る。
4. **MISTEMS 固有の文脈。** 本フォークはチャンネル体験の拡張 (チャンネル一覧強化、チャンネルリノートの出所表示など) を重ねており、チャンネルが利用の中心にあるサーバー向けである。だからこそ「既存チャンネルの非連合の期待を壊さない」オプトイン設計の優先度は上流よりさらに高い。逆に、連合チャンネルが立ち上がれば、小規模サーバー同士が話題単位でつながる手段としてフォークの価値の柱になり得る。まず Phase 1 (unlisted + Actor + メタデータ) を小さく出し、yojo-art 系サーバーとの相互運用実験を Phase 2-3 の仕様確定に使う、という進め方を推奨する。

## 6. 結論

- 当初計画の核 (オプトイン、unlisted 送出、`_misskey_channel`、段階的導入) は比較後も妥当。
- ただし Actor 生成は yojo-art の実証により「安い」ことが分かったので Phase 1 に前倒しし、`audience` の URI を最初から解決可能にする。
- 受信判定は yojo-art と逆に audience を一次、メンションをフォールバックにする。
- Announce 中継は Create だけでなく Update / Delete まで設計に含める (yojo-art の落とし穴の回避)。
- モデレーション語彙は本家ドラフトの受信側義務をそのまま実装し、将来の本家実装との整合点として確保する。
