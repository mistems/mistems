# 使われていないインデックスの整理

作成日: 2026-11-12。状態: A は migration `1794546098079-drop-unused-indexes.js` として実装済み（2026-11-13）。本番では、まだ何もしていない

## 背景

- honban-ops が 3 台（gamelore・systems・favskey）の `pg_stat_user_indexes` を診断した
  - 診断の全体: `honban-ops/logs/2026-11-12-PostgreSQL診断スキルでのDB診断.md`
  - 候補の表: `honban-ops/logs/2026-11-12-PostgreSQL診断スキルでのDB診断/20-index-candidates.md`
- 3 台とも `idx_scan` が 100 以下のインデックスは 84 個ある。主キー・一意・制約のインデックスは除いてある
  - 大きさの合計は gamelore 2.7GB、systems 1.7GB、favskey 2.1GB である
- これとは別に、先頭の列が別のインデックスに含まれる冗長なインデックスが 21 個ある
- gamelore では、投稿の INSERT が DB 時間の約 21% を占める。note・drive_file・hashtag への書き込みを軽くしたい
- インデックスを消すと、次の 2 つが得られる
  - 書き込みのたびに走るインデックスの更新が減る
  - 索引のある列を UPDATE しなくなれば、その更新が HOT update になれる。HOT update は新しい行をテーブルのページ内に置けるので、インデックスを書き換えずに済み、テーブルも膨らみにくい

## コードで使われているかの確認

mistems-main の `packages/backend/src` で、各列を条件・並べ替え・結合に使うクエリを調べた。

- 候補の列には、ほかのテーブルを参照する FK はない。このため、親テーブルの行を消すときの ON DELETE CASCADE にも使われない
- 定義元は、`note.threadId` を除いてすべて上流のエンティティの `@Index` である

### A. 消す（クエリがないか、あってもこのインデックスでは引けない）

`index-optimize` の migration `1794546098079-drop-unused-indexes.js` で、次の 25 個を消す。合計は gamelore 約 2.6GB、systems 約 1.7GB、favskey 約 2.0GB である。

| インデックス | 大きさ (gamelore) | 確認したこと |
|---|---|---|
| `drive_file (uri)` `IDX_e5848eac4940934e23dbc17581` | 1837MB | 使うのは `DriveService.ts` の `findOneBy({ uri, userId })` の 1 か所だけである。重複キーのエラーを受けたときの分岐だが、uri の UNIQUE はない（drive_file の UNIQUE は accessKey の 3 列だけ）ので、この分岐は実際には実行されない。実行されたとしても `(userId, folderId, id)` で引ける |
| `drive_file (isSensitive)` / `(maybeSensitive)` / `(maybePorn)` | 各 102〜103MB | クエリはなく、書き込みと値の読み出しだけである |
| `drive_file (type)` `IDX_a40b8df8c989d7db937ea27cf6` | 104MB | 一般ユーザー向けの API は `userId` との組み合わせで引くので、複合インデックスを使う。管理画面の `type LIKE 'image/%'` は、照合順序が C 以外なのでこのインデックスを使えない |
| `drive_file (isLink)` `IDX_315c779174fe8247ab324f036e` | 105MB | どのクエリも `(userId, isLink)` か、MISTEMS の部分インデックス（`IDX_drive_file_userId_size_notlink`）を使う |

| `user (tags)` `IDX_fa99d777623947a5b05f394cae` | 53MB | `hashtags/users` は `:tag <@ user.tags` で引くが、このインデックスは配列の btree なので `<@` には使えない |

| `antenna (lastUsedAt)`・`clip (lastClippedAt)` | 5MB・3MB | クエリはなく、更新だけである。どちらも頻繁に更新される列なので、索引を外す効果は大きさより大きい |
| `channel (notesCount)`・`(usersCount)` | 0MB | クエリはなく、増やすだけである。チャンネルに投稿するたびに更新される |

### B. 残す（実際に使われる経路がある）

| インデックス | 使っているところ |
|---|---|
| `drive_file (userHost)` | `admin/federation/delete-all-files` の `findBy({ userHost })` と、`CleanRemoteFilesProcessorService`。どちらも頻度は低い。ただし、索引がないと、サーバー単位でファイルを全部消す操作が 1 千万行規模の全件走査になる |
| `poll (userHost)` | `notes/polls/recommendation` の `userHost IS NULL`（「みつける」のアンケート） |
| `instance (firstRetrievedAt)` | `federation/instances` の並べ替え（連合の画面で選べる） |
| `gallery_post (likedCount)` | `gallery/popular` |
| `emoji (roleIdsThatCanBeUsedThisEmojiAsReaction)` (GIN) | 管理画面の絵文字検索 |

### C. 効きは薄いが、残しても困らない（小さいテーブル、または選択性が低い）

- 対象: `user (isExplorable)`、`poll (userId / channelId)`、`abuse_user_report (targetUserHost / reporterHost)`、`ad (expiresAt / startsAt)`、`role_assignment (expiresAt)`、`user_list (isPublic)`、`channel (isArchived)`、`webhook`・`system_webhook`・`announcement` などの真偽値の列
- どれも数 MB 以下で、書き込みも少ない。消すと上流との差が増えるわりに得るものが少ないので、今回は触らない

### D. 使われていない古いテーブル（別の計画にする）

- 対象: `messaging_message`、`user_group`、`user_group_joining`、`user_group_invite`、`user_group_invitation`、`note_watching`、`reversi_matching`
- エンティティもコードもない。上流の migration は、これらのテーブルを DROP していない
- これらの FK は ON DELETE CASCADE のまま残っている。このため user・note・drive_file の行を消すたびに、これらのテーブルへの参照の検査が実行される
- インデックスだけを消すと、この検査が全件走査になる。消すならテーブルごと消す
- テーブルを消すとデータは戻せない（`down()` で中身を戻せない）。このため、本番のデータの量を見てから、別の計画書で扱う
- `promo_note` と `promo_read` はエンティティがあり、今も使われているので対象外である

### E. 冗長なインデックス 21 個

- 先頭の列が、複合（一意）インデックスの先頭の列と同じものである（例: `clip_note (noteId)` ⊂ `(noteId, clipId)`）
- migration 1783062429920 で following・muting・blocking などを消したのと同じ扱いで消せる
- どれも小さいテーブルなので効果は小さい。A を入れたあと、本番の大きさを見て、大きいもの（`user_ip`、`clip_note`、`renote_muting` など）から入れる
- `registration_ticket` の `IDX_b6f93f2f30bdbb9a5ebdc7c718` は、一意制約 `UQ_b6f93f2f30bdbb9a5ebdc7c7189` と同じ列の重複である

## 上流のエンティティが作るインデックスの扱い

前例: migration 1783062429920（following・muting・blocking などの冗長なインデックスを消したもの）

1. **エンティティの `@Index()` を外し、理由をコメントに残す**
   - 外さないと `check-migrations` が「作り直す DDL」を出し、次の `migration:generate` で戻ってしまう
   - 前例の `Following.ts` は `// Covered by the composite index (...)` に置き換えている
   - 名前付きで残したいもの（MISTEMS の部分インデックスなど）は、`{ synchronize: false }` で宣言だけ残す
2. **MISTEMS の migration で `DROP INDEX [CONCURRENTLY] IF EXISTS` する**
   - `index-optimize` の migration と同じ冪等なヘルパーを使い、`MISSKEY_MIGRATION_CREATE_INDEX_CONCURRENTLY=1` で CONCURRENTLY にする
   - `down()` では、上流と同じ名前・定義で作り直す
3. **上流との差のリスク**
   - **上流のエンティティの同じ行が変わると、統合でコンフリクトする。** 1 列 1 行の差なので、rerere に覚えさせる
   - **上流が、あとからその列で引くクエリを足すかもしれない。** 統合のたびに `git diff <前回の origin/develop>..origin/develop -- packages/backend/src` で、消した列名（`uri`・`threadId`・`tags` など）を引くクエリが増えていないかを見る。増えていたら、MISTEMS の migration で作り直す
   - **上流の migration が、消したインデックスの名前を `IF EXISTS` なしで DROP や RENAME するかもしれない。** 上流は名前を決め打ちで書くことが多いので、その migration が失敗する。統合のたびに、上流の新しい migration に消したインデックス名が出てこないかを `grep` で見る。出てきたら、その migration の前に作り直す migration を MISTEMS 側に足す
4. 上流に提案できるもの（`drive_file (uri)` の未使用など）は、MISTEMS では先に消し、上流で同じ変更が入ったら「栄誉の殿堂」に移す

## 進め方

1. **前提をそろえる**
   - 3 台の `pg_stat_database.stats_reset` を見て、統計が十分な期間（少なくとも数週間）たまっていることを確かめる
   - 月に 1 回しか動かない処理（チャートの再同期など）が統計の期間に入っているかも確かめる
2. **A を 1 本の migration にする（実装済み）**
   - `index-optimize` の `1794546098079-drop-unused-indexes.js` に入れた。上流のエンティティの `@Index` も同じコミットで外し、コメントに置き換えた
   - `hashtag` の件数の列は、`IDX_hashtag_name_pattern` ができたあとに消す必要がある。前方一致のインデックスの migration（`1794493981000`）より後のタイムスタンプにしたので、デプロイで適用する順番はこれで守られる
   - 本番で手で先に消すときも、`IDX_hashtag_name_pattern` を作り、`hashtags/search` の EXPLAIN でそれを使うことを確かめてから、件数の列を消す
   - テスト用の DB（照合順序は en_US.utf8）で、次のことを確かめた
     - 適用すると 25 個が消える
     - `migration:revert` で、本番の `pg_get_indexdef()` と同じ定義の 25 個に戻る
     - `MISSKEY_MIGRATION_CREATE_INDEX_CONCURRENTLY=1` のときは `DROP INDEX CONCURRENTLY` になる
     - `check-migrations` と `migration:generate --dryrun` で、差分が出ない
3. **本番での削除**
   - honban-ops で、1 台ずつ `DROP INDEX CONCURRENTLY` を手で実行する。migration は「なければ何もしない」ので、手で消したあとにデプロイしても困らない
   - 消す前に、`pg_get_indexdef()` で定義を控えておく（戻すときに使う）
   - 消したあとの数日、`pg_stat_statements` で該当のテーブルの遅いクエリが増えていないかを見る
4. **E（冗長）と D（古いテーブル）は、A のあとに別に扱う**

## 期待する効果（gamelore）

- A の合計は約 2.6GB である（`drive_file (uri)` の 1.8GB が大半）
- `drive_file` への INSERT 1 回で更新するインデックスが 7 つ減る
- `hashtag`・`channel`・`antenna`・`clip` の件数や日時を更新するときに、HOT update になれる
